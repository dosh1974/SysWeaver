## What users feel

1. Nothing moves under the pointer: no jumps while loading, bars and buttons stay put.
2. Nothing is lost: typed text survives a reload or a dropped connection; closing or leaving with unsaved edits asks first.
3. Work sent to the background stays findable in one place, also on a phone.
4. Nothing is destroyed by accident: what can't be brought back asks first and names what it destroys; what stays reversible just runs and offers Undo.
5. Every click, tap and key reacts at once, also when it is refused (and says why); long work shows progress; a busy button can't run twice.
6. Mouse, touch, keyboard and screen reader all reach every function; a click with Ctrl or Shift held never runs an action by accident, it moves the focus; the keyboard focus is visible while the keyboard is in use.
7. Every action says what it will do; there is no repeated helper text and no permanent "how to" text once it is learned.
8. Text is selectable where it is content, values that are needed elsewhere copy in one step, the UI chrome is never selected by accident.
9. Every page works in every language, theme, zoom level and on a phone.

## How to read and audit

- **MUST** rules are required; a page that breaks one is a bug (or has a waiver, below). **SHOULD** rules are the default; break one only for a reason written in the page's code or README. **MAY** marks an allowed option.
- Every rule has an id (`UX-<area>-<n>`, written without `UX-` inside the guide). Ids are never reused. Withdrawn: TIP-3 (merged into INP-12), LST-1 (into LAY-4), SEC-3 (into SAF-7), TXT-7 (placeholder syntax, now Appendix A).
- **owner** marks a rule set by the product owner: it may be clarified or extended, never removed or weakened.
- After the level each rule says **who** implements it and **how** it is checked: `F` = the framework does it (a page gets it by using the components), `P` = the page author, `F+P` = both; `lint:<rule>` = found by `SwWeb check`, `auto` = an automated browser test can decide it (until that test exists, the auditor checks by hand), `manual` = a review decides it. WCAG numbers in brackets (ex: [2.4.7]) name the WCAG 2.2 success criterion a rule implements.
- **Framework first.** When a rule needs code, the code belongs in the shared layers (`Sw.*` components, tokens, the shell), not in one page. A page that has to work around a component to follow a rule means the component needs fixing.

**Audit findings.** One finding per rule per page, listing every element it affects ("INP-11, Services page: 14 cards and 3 icon buttons have no hover"); it names the guide version, the rule id, the page and the severity of its worst element. Severity follows the user impact:

| Severity | When |
|---|---|
| **Blocker** | Data loss; a destructive action without confirmation (SAF-1; also a delete that is final after its Undo, SAF-5); a function that mouse, touch, keyboard or a screen reader can't reach |
| **Major** | A broken owner rule or WCAG 2.2 AA criterion that users meet on the page's main task |
| **Minor** | Everything else: other broken MUST rules, owner or WCAG breaks off the main task, a SHOULD broken without a written reason |

A SHOULD broken for a reason written in the page's code or README is not a finding. A finding on the `F` part of a rule whose [Framework support](#framework-support) row says Missing or Partial is filed **once, against the framework** (citing the row), not against each page; page audits check that part again when the row says Supported. Routing is not a waiver: the page doesn't conform until the row is Supported (section 12). A page that works around a component is filed against the page and the component.

**Waivers (owner).** A MUST may be waived for one page by an entry in the page's README: rule id, reason, approved by (the product owner), expiry (at most 2 releases). The audit report lists active waivers and doesn't count them as findings; an expired waiver is a finding again. Blockers can't be waived, and a waived WCAG rule stays a known failure in any accessibility statement.

### Glossary

| Term | Meaning |
|---|---|
| Pure click | A primary click (left button, touch tap, pen tap, or a `click` sent by the keyboard or assistive technology) with no Shift, Ctrl, Alt or Meta held (`Sw.IsPureEvent`). |
| Pop-up | Anything drawn above the page that takes attention: context and dropdown menus, dialogs, sheets, pickers, popovers with controls. Not tool tips, not toasts. |
| Scrim | The full window layer under a pop-up that catches the pointer: transparent for menus, dimmed for dialogs. |
| Sheet | A dialog docked full width to the bottom of a narrow screen. |
| Toast | A short message at the edge of the screen that goes away by itself ("Saved"). |
| Skeleton | Placeholder shapes in the size of content that is still loading. |
| Inert | The HTML `inert` attribute: the element and its content can't be clicked, focused or read by a screen reader. |
| Tabular figures | Digits of equal width (`font-variant-numeric: tabular-nums`), so changing numbers don't move. |
| Dirty | At least one field's value differs from its value when the page / dialog opened or was last saved (typing and undoing it is not dirty); a restored draft makes its form dirty. |
| Modifier click | A left click with Shift, Ctrl, Alt or Meta held. It moves the keyboard focus and never runs the pure click's action (UX-INP-2). Enter / Space with a modifier held is a key combination (INP-22 / 23), not a modifier click. |
| Busy | A dialog or control whose action is still running (a save, a long job); exposed as `aria-busy="true"` (FBK-2). |
| Close attempt | Any way a user tries to close a pop-up: its close button (×, also by voice or assistive technology), its footer Cancel / Close, Escape, an outside click or tap (the scrim, or the dimmed area above a sheet), a swipe down on a sheet, the browser's Back (phone gesture, browser button, mouse back button; MOB-3), closing or reloading the tab. What each does in a dirty or busy dialog: the table in UX-POP-6. |
| Phone layout | A viewport at most 760 CSS px wide **or** at most 500 px high (the framework's breakpoints), regardless of the device; a desktop zoomed to 400 % is in it. When both hold, the ≤ 500 px high rule wins (dialogs fill the viewport, no sheet), as in `overlays.css`. |
| On touch | The primary pointer is coarse (`pointer: coarse`) or the last pointer input was touch, in any layout; a touchscreen laptop counts while it is touched. |
| Tap | A touch press and release that moved at most 10 px. A larger move is a drag or a scroll: it is not a tap and cancels a pending long press. |
| Destructive | An action whose result the user can't revert, or can revert only through an Undo that expires (delete, kill, revoke, overwrite, send to other people). |
| Chrome | The UI around content: buttons, menus, short labels, headers, toolbars, card frames, icons. |
| Roving tabindex | One Tab stop per composite widget (menu, grid, tab list); arrow keys move inside it. |

## 1. Input: pointer, touch and keyboard

### Clicks

- **UX-INP-1 (MUST, owner) Act only on pure clicks.** `F+P · lint:a11y-custom-control, auto` Actions are bound to the `click` event (which mouse, touch, pen, Enter / Space, screen readers and voice control all fire), never to `pointerdown` / `pointerup` alone, and run only when the click is pure: test with `Sw.IsPureEvent(ev)` or `Sw.BadClick(ev)` (which also stops the event). A synthetic click from assistive technology (`detail === 0`) is pure. INP-1 and INP-2 are about pointer clicks; key combinations (Ctrl+Enter, Shift+F10 …), also Enter / Space with a modifier held, follow INP-22 / 23.
- **UX-INP-2 (MUST, owner) A modifier click moves the focus and never runs the click's action.** `F+P · auto` *Why: there is always a safe way to move the keyboard focus with the mouse, also onto table data that has no click action.* In short: Shift / Ctrl / Alt / Meta + click puts the focus there and does nothing a pure click would do.
  - **Never:** no action, no open, no navigation in the current tab, no menu, no edit, no "select only this item".
  - **Always:** focus the element if it is interactive, else the list / table item it belongs to (cell, row, card, list item, tree node); static text behaves as in the browser (no focus). The framework focuses in code where the browser doesn't (Safari doesn't focus a clicked button).
  - **Shown:** a composite widget shows its current item (FOC-3); any other element gets the ring through `focus({ focusVisible: true })`; where a browser ignores that option, the same `--sw-focus` outline through a class removed on the next pointer down.
  - **May:** Shift+click extends a text selection (in a field a modifier click places the caret); in lists, tables and trees with multiple selection Ctrl+click (Meta+click on macOS) toggles and Shift+click extends from the anchor (without multiple selection they only focus); a real `<a href>` keeps the browser's link gestures (never a click handler where a link belongs), except that **Alt+click on a link in a data table or listing copies its address** with a toast (`Sw.Clipboard.AltClickLinks`; the original SysWeaver tables copied on a modifier click; Ctrl / Meta / Shift + click and the middle button stay the browser's), and the cell menu of a link cell has "Copy link". Every such selection also works with checkboxes and keys (Space, Shift+Arrow).
- **UX-INP-3 (MUST, owner) Menu buttons also open on a pure right click.** `F · auto` An element whose pure left click opens a context menu (a "⋮" button, a row menu, a menu button) also opens it on a pure right click (call `preventDefault()` only then), with the Menu key and with Shift+F10 when focused; it has `aria-haspopup="menu"` and `aria-expanded`. A right click with a modifier is left alone, so the browser menu appears ("Inspect", copy, spell check); on macOS Ctrl+click counts as a right click. The right click is never the only path: every context menu item is also reachable from a visible button or the row menu.
- **UX-INP-4 (MUST) No browser context menu takeover elsewhere.** `F+P · manual` Elements without a menu of their own never block the browser's context menu; text fields always keep it.
- **UX-INP-5 (SHOULD) Long press = right click on touch.** `F · auto` A long press of 500–600 ms (the framework uses 550 ms; a move beyond the tap threshold, 10 px, or the start of a drag cancels it) on an element with a context menu opens the menu (`Sw.LongPress`), never its tool tip; on an element without one it shows the tool tip (`Sw.Hint`, TIP-4). A long press never triggers the primary action.
- **UX-INP-6 (MUST) Double click is never the only way.** `P · manual` A double click may be a shortcut; the same result is reachable with a single pure click, a menu item or a key.
- **UX-INP-7 (MUST) Act on release, cancel by moving away.** `F · auto` The action runs on `click` (released over the element where it was pressed), so a press can be cancelled by moving off. Drags start after a dead zone of 4 px (mouse, pen) or 10 px (touch, the tap threshold). Exception: press-and-hold repeat buttons (increment) act on press, and also on a plain `click` so assistive technology can use them.
- **UX-INP-8 (MUST) No action on hover alone.** `P · manual` Hover may show a tool tip or a preview; it never changes data, opens a menu that takes focus, or navigates.

### Cursor and hover

- **UX-INP-10 (MUST, owner) Every mouse interactive element shows its cursor**: `F+P · auto` `pointer` for things that act on click (buttons, links, toggles, menu items, clickable rows and cells), `text` for editable text, `grab` / `grabbing` for drag handles, `col-resize` / `row-resize` / `nwse-resize` for splitters and resize handles, `not-allowed` for disabled controls, `progress` on a busy control only, `help` only for pure help icons, never `wait` / `progress` on the whole page.
- **UX-INP-11 (MUST, owner) Every mouse interactive element has a hover effect.** `F+P · auto` The hover state differs from the rest state in at least one of background (the `--sw-hover` tone, as the components use), border colour, icon colour or underline (links), uses theme tokens, transitions with `--sw-dur-1`, and applies only under `@media (hover: hover)` so touch screens never keep a stuck hover.
- **UX-INP-12 (MUST) Disabled looks disabled, stays reachable and says why.** `F · auto` A disabled control is muted, keeps its place, has `cursor: not-allowed`, uses `aria-disabled="true"` (not the `disabled` attribute, so it stays focusable and its reason can be read) and ignores activation; its tool tip says why and what enables it ("Select a row first", "Your role doesn't allow this"), and an activation attempt shows and announces that reason at once (FBK-1): a tool tip bubble anchored to the control (`Sw.Hint`, also on touch, for at least 3 s or until the next input) and `Sw.Page.Announce`.

### Keyboard, touch and mouse parity

- **UX-INP-20 (MUST, owner) Everything works with mouse, touch and keyboard alone.** `F+P · manual` Every action, menu, drag, resize, sort, filter and selection has a keyboard path and a touch path, and every drag has a single pointer alternative [2.5.7]. Path and multipoint gestures (swipe a sheet or a toast away, swipe between tabs, pinch to zoom a chart) are never the only way: each has a visible single tap / click alternative [2.5.1]. Examples: drag to reorder also has Alt+Up / Alt+Down and "Move up / down" in a menu; a column resize also has a menu or keys; hover-only actions are always visible on touch.
- **UX-INP-21 (MUST) Native elements first.** `P · lint:a11y-custom-control` Use `<button>`, `<a href>`, `<input>`, `<select>` (or the `Sw` controls). A non-native clickable element gets `tabindex`, a role, Enter / Space and a name (`Sw.KeyClick(e)` does the keyboard part).
- **UX-INP-22 (MUST) Standard keys.** `F+P · auto` Enter / Space activate; Escape closes the innermost open thing (UX-POP-3); in a text field outside a dialog it keeps the typed text, as the original inputs (1.7.0; a field may opt into reverting it); Tab / Shift+Tab follow the visual order; arrow keys move inside composite widgets (roving tabindex); Home / End go to the first / last item; type-ahead in menus and lists.
- **UX-INP-23 (MUST) Shortcuts never steal text input.** `F+P · auto` A single-key shortcut never fires while focus is in a text field; page shortcuts use a modifier or are scoped to a focused widget, never Alt+Left / Alt+Right (browser Back / Forward), and are named in the element's tool tip ("Delete (Del)").
- **UX-INP-24 (MUST) Touch targets.** `F+P · auto` At least 24 × 24 CSS px everywhere [2.5.8] and 44 × 44 px in the touch density, with at least 8 px between neighbouring touch targets. The 2.5.8 exceptions apply: links inside running text, and the browser's own unstyled controls.
- **UX-INP-25 (MUST) No zoom lock.** `F+P · auto` Never set `user-scalable=no` or `maximum-scale=1`; pages reflow up to 400 % zoom (UX-ACC-6).

### Selection and copy

- **UX-INP-30 (MUST, owner) Selection off for chrome, on for content.** `F+P · auto`
  - Off by default: the theme sets `user-select: none` on the body, so a double click or a drag never paints chrome blue.
  - On (`.sw-selectable`) for content: values, ids, messages, logs, code, error details, table cell values, and all sentence text (dialog messages, help and hints, empty states, status and error lines, toast texts, form rules), because text-to-speech tools (Speak Selection, Read&Write, "Read aloud") read the selection. A `role="status"` / `alert` region is never `user-select: none`.
  - Inputs, text areas and `[contenteditable]` set `user-select: text` and `-webkit-user-select: text` explicitly (some iOS Safari versions make fields untypeable otherwise).
  - Text is selected by a drag, a double click on a word or Shift+click to extend (INP-2); these belong to the browser: no `selectstart` handlers. In a list with multiple selection, Shift+click on a row extends the item selection instead (INP-2); drag selects its text. A row that opens on a double click (INP-6) doesn't also select a word; its text stays selectable by drag.
- **UX-INP-31 (SHOULD, owner) Easy copy for values needed elsewhere.** `F+P · manual` Values users commonly paste elsewhere (ids, keys, tokens, URLs, hashes, error details, configuration lines, addresses, log lines) get a one step copy: a copy button next to the value (on touch visible and 44 × 44 px, not only in a menu), the cell / row menu ("Copy value", "Copy row") or Ctrl+C on the focused cell. It copies exactly the value (no label, no thousands separators or units unless they are part of the value). A value that the original UI copied on a click (`copyOnClick`: table cells, facts, chips) still copies on a plain left click or tap (1.6.0, owner: no gap to the old behaviour; the owner's rule is "easy copy for values users need, not everywhere"); a click with a modifier, a click while text is selected in it and a click on a link inside it don't copy. A copy button confirms in place: its icon becomes a check mark for 1.5 s, its tool tip says "Copied", and `role="status"` announces what was copied ("API key copied"); a toast naming the value is used only where there is no button (menu item, Ctrl+C). Not every value: names, counts and status words need no copy action.
  - Example: an API key row shows the masked key and a copy button "Copy the API key (not shown)"; the table cell menu has "Copy value"; an error toast has "Copy" for support.

## 2. Pop-ups: menus, dialogs, pickers, popovers

- **UX-POP-1 (MUST, owner) A pop-up blocks all other input.** `F · auto` While a pop-up is open nothing behind it reacts to the pointer, keys or touch: not the page, not the shell, not other frames. One scrim covers the whole app (the shell included, also for pop-ups opened in a framed page), never a double dim. Everything behind a modal pop-up is `inert`, so screen reader browse mode and swipe can't leave it. Above the blocker sit only: the pop-up's own nested levels, tool tips of elements inside it, toasts and the session time-out warning (POP-5). While a modal is open, toasts and the `Sw.Page.Announce` live region sit inside its subtree (or the same top layer), never in the inert background, so they are announced and toast buttons are in the dialog's Tab cycle; a toast never takes the focus.
- **UX-POP-2 (MUST, owner) Clicking outside closes, and does nothing else.** `F · auto` The `pointerdown` outside closes the pop-up (menus, pickers, popovers, dialogs that are neither dirty nor busy); that pointer's `pointerup`, `click` and `contextmenu`, and hover until the pointer moves, are swallowed: the element behind is not activated, focused or hovered. One outside click = close, a second click = act. On touch the close happens on release of a tap (glossary), so a scroll gesture outside doesn't close a picker.
  - **Exception (owner): a busy or dirty dialog doesn't close silently** (POP-6). An outside click (or a tap on the dimmed area above a sheet) is still swallowed and closes nothing, and gives the rejection cue (POP-6).
- **UX-POP-3 (MUST) Escape closes the innermost thing.** `F · auto` Order: a visible tool tip or hint bubble (TIP-5, INP-12) → an open list inside a field (combobox, autocomplete) → the top pop-up level (one level per Escape) → never the page. Escape never reverts typed text (1.7.0, as the original inputs; it was "the current edit" before). In a dirty or busy dialog Escape is a close attempt (POP-6).
- **UX-POP-4 (MUST) Focus goes in and comes back.** `F · auto` Opening moves focus into the pop-up (UX-FOC-2); Tab cycles inside it; closing returns focus to the opener or, if it is gone, to the next item, else the previous one, else the container's heading. Dialogs have `role="dialog"` (`alertdialog` for confirmations), `aria-modal="true"`, `aria-labelledby` the title and `aria-describedby` the message.
- **UX-POP-5 (MUST) One pop-up layer at a time**, except a sub menu or a confirmation opened from inside a pop-up, and the session time-out warning (ACC-7), which opens above any pop-up, takes the focus and returns it to where it was [2.2.1]. `F · auto`
- **UX-POP-6 (MUST, owner) Busy and dirty dialogs never close silently.** `F+P · auto, manual` Every close attempt (glossary) does what this table says; POP-2, POP-3, POP-7, MOB-3 and FBK-1 refer to it. Dirty ends with a save (glossary), so a dialog that saved closes without asking.

  | Close attempt | Clean | Dirty | Busy | Busy + dirty |
  |---|---|---|---|---|
  | Close button (×) | Closes | Asks "Discard changes?" | Acts as "Continue in background" when offered (its tool tip then says "Close; the work goes on"), else the rejection cue; never an implicit Cancel | Rejection cue until the work ends, then as dirty |
  | Footer Cancel / Close | Closes | Asks "Discard changes?" | Cancel, or a Close that names a consequence ("Close (the upload stops)"), stops the work, then as clean / dirty (a progress-only dialog closes); a plain Close acts as × | Cancel or a Close that names a consequence stops the work, then as dirty; a plain Close acts as × |
  | Escape | Closes | Asks "Discard changes?" | Rejection cue | Rejection cue |
  | Outside click / tap | Closes | Rejection cue | Rejection cue | Rejection cue |
  | Swipe down (sheet), browser Back | Closes | Stays open, asks "Discard changes?" | Stays open, rejection cue | Stays open, rejection cue |
  | Tab close / reload | Closes | `beforeunload` prompt (SAF-10) | `beforeunload` prompt if the work stops with the page, else closes | `beforeunload` prompt |
  | "Continue in background" | n/a | n/a | Closes, the job goes on (below) | Asks "Discard changes?" first, unless the unsaved input was sent with the job |

  - **"Discard changes?"** is a confirmation ("Discard" / "Keep editing", Keep editing focused); any close attempt on it means Keep editing. *Why it asks instead of keeping a draft:* owner answer 2 says a dialog with unsaved input asks, and drafts (SAF-11) cover only text, never secrets.
  - **Rejection cue** (FBK-1): within 100 ms the dialog pulses once (`--sw-dur-2`; none with zero motion) and a line after the title says which button to use, naming only the buttons shown by their visible labels: `_T("Unsaved changes: use {0} or {1}", saveLabel, cancelLabel, "…")`, `_T("Still working: use {0} or {1}", …)` or `_T("Still working: use {0}", …)` for one button; busy + dirty shows the busy message. One line at 390 px in English; the reserved space fits two lines (translations, 400 % zoom), or the line overlays the content, never shifting it or covering the buttons or the focus; part of the dialog's text (`aria-describedby`, selectable); stays until the state changes.
  - **Announced** on every attempt (`Sw.Page.Announce`, from inside the dialog, POP-1; repeats within 1 s once, FBK-1); focus stays; never a toast or another dialog.
  - **Ways out of a busy dialog:** Cancel when the work can be cancelled (a plain stop is not destructive; one that throws away finished work is, SAF-1). **"Continue in background"** (the one label everywhere; tool tip "Close this dialog; the work goes on and you are told when it is done") only when the work survives closing the dialog and in-app navigation (a server job or a shell-level task), and only once the activity list (FBK-4) is Supported; it announces "Continuing in the background" and returns focus to the opener (POP-4).
  - **A busy dialog with neither button** is allowed only for work that normally ends within 10 s and shows progress (FBK-4). At 10 s it adds, in reserved space, Cancel (or, when the work can't be stopped, "Close" naming the consequence, "Close (the upload stops)", which acts as Cancel: it stops the work, then acts as clean / dirty, so a dirty dialog still asks; never both) and "Continue in background" when allowed, announced once with the labels of the added buttons (as the rejection message: `_T("Still working: use {0} or {1}", …)`), focus stays. Closing by itself returns focus to the opener (POP-4) and shows the result (FBK-5).
- **UX-POP-7 (MUST, owner) Dialogs are movable and resizable, and remember it.** `F · auto`
  - Move by dragging the title bar; resize from edges and corners (8 px handles), within the dialog's minimum and maximum sizes; a double click on the title bar maximizes / restores (the desktop habit).
  - Keyboard: the **dialog menu** (a "⋮" button in the title bar, "Dialog options") has Move, Size, Maximize / Restore and Reset position. Move and Size enter a mode: arrows move / resize by 10 px (Shift: 50 px), Enter keeps, Escape reverts; the new position is announced. No Alt+arrow keys (Alt+Left / Right is browser Back / Forward).
  - Without dragging [2.5.7]: in Move and Size mode the dialog shows step buttons (↑ ↓ ← →, 44 px on touch, tool tips "Move up 50 px", "Make wider 50 px" …) next to Done and Revert, so a single click or tap does everything a drag does; Maximize / Restore and Reset position are single clicks in the dialog menu.
  - Position and size are remembered per dialog kind (a stable dialog id) in local storage and restored clamped: never larger than the viewport, the whole title bar inside it, and never smaller than the content needs at the current zoom (no two way scrolling).
  - In the phone layout dialogs are not movable: at most 500 px high they fill the viewport (this wins when both conditions hold); otherwise, at most 760 px wide, they are full width sheets (resized by the sheet handle or the dialog menu's Size, closed by swiping down or by the always visible close button, both close attempts per POP-6). Context menus and pickers are anchored and not movable.
- **UX-POP-8 (MUST) Pop-ups stay on screen** and next to their anchor (flip when there is no room), follow the anchor on scroll or close when it scrolls away, and never cause page scrolling (`Sw.Place` / `Sw.Track`). `F · auto`
- **UX-POP-9 (MUST) Every dialog has a title** that says what it is about ("Delete appsettings.json?") and a close button with a tool tip. Buttons are verbs ("Delete", "Save", "Cancel"), never "OK" / "Yes" / "No". `F+P · lint:design-confirm, auto`
- **UX-POP-10 (MUST) Background scroll is locked** while a modal pop-up is open, without a layout shift (keep the scrollbar gutter). `F · auto`
- **UX-POP-11 (SHOULD) No pop-up opens by itself** (no surprise dialogs on load, no modal for information a toast or an inline message can carry). `P · manual`
- **UX-POP-12 (SHOULD) Short, grouped menus.** `P · manual` At most 10 items per group, groups separated by function, frequent items first, destructive items last (UX-SAF-3); more items go into a sub menu or a dialog.

## 3. Keyboard focus

- **UX-FOC-1 (MUST) Focus is always somewhere sensible.** `F+P · auto` After an action (closing a dialog, deleting a row, a save, a list reload) focus is never on `<body>`: it goes to the element that started the action, its replacement or the next item.
- **UX-FOC-2 (MUST, owner) Best initial focus.** `F+P · auto` On entering a page: the first field of a form page, the search box of a list page, else the page's `h1` (`tabindex="-1"`); never the shell menu, never a destructive button. In a dialog: the first field, else the primary safe button; in a destructive confirmation **Cancel**. In a menu: the first enabled item (never a destructive one). In the phone layout and on touch, a text field is not focused automatically if that would open the on-screen keyboard unasked.
- **UX-FOC-3 (MUST, owner) The focus ring follows the browser default (`:focus-visible`).** `F+P · lint:a11y-focus, auto` The ring shows on keyboard focus and hides on mouse / pointer interaction, as the browser decides (browsers also show it when a text field is focused by the pointer: that conforms; after a modifier click see INP-2); no custom keyboard-mode timer, never `:focus` alone for the ring, never `outline: none` without a replacement in the same rule [2.4.7].
  - **The ring** appears at once (MOT-1): a CSS `outline` (so it survives forced colors) of at least 2 px in `--sw-focus`, 3:1 against its surroundings [2.4.11; 2.4.13 as a target], never clipped by `overflow` or covered by a neighbour (use `outline-offset` or an inset ring inside scrollers). Text fields always show their caret and active border.
  - **The current item** of a composite widget (grid, list, menu, tabs) always shows as a state, with or without a ring, also after a pointer or modifier click (INP-2): visibly different from the selected state (a multi-select grid shows both), 3:1 against its neighbours [1.4.11], and kept under forced colors (an outline or `Highlight` border, not only a tonal background).
  - **Optional (MAY):** a setting "Always show focus" that also shows the ring on pointer focus, for users who mix mouse and keyboard. `:focus-visible` already meets 2.4.7, so it isn't required; if offered it sits in the shell settings (also on the sign-in page), applies at once, is stored per user and is on by default under `forced-colors: active` or `prefers-contrast: more`.
- **UX-FOC-4 (MUST) Focus order follows the visual order** (no positive `tabindex`); hidden or collapsed content is not focusable; a focused element is scrolled into view and never hidden under a sticky bar, toast or the on-screen keyboard [2.4.3, 2.4.11]. `F+P · auto`
- **UX-FOC-5 (MUST) A skip link** "Skip to content" is the first tab stop (the shell provides it). `F · auto`
- **UX-FOC-6 (MUST) Page changes are announced.** `F · auto` On in-app navigation `document.title` becomes the page name (as in the menu), focus moves as in FOC-2, and screen readers hear the new page name.

## 4. Feedback for actions and async work

- **UX-FBK-1 (MUST, owner) Immediate visual response, also to a refusal.** `F+P · auto` Every attempted action gives a visual cue within 100 ms that it started, **or that it was rejected and why**. An *attempted action* is any activation of an interactive element, enabled or `aria-disabled` (click, tap, Enter / Space, right click, long press, Menu key, Shift+F10, a voice command), a drag start, a documented shortcut, a submit, a drop or a close attempt; not a click on static content, not typing (FRM-3).
  - **Started** → the pressed state, then busy, progress, a skeleton or a toast. A modifier click → the focus shown where it went (INP-2).
  - **Absorbed** (not a rejection): a repeated activation of a busy button; its busy state is the cue and nothing more is announced (FBK-2).
  - **Rejected** → a disabled control, or a shortcut to one: its reason (INP-12); a busy or dirty dialog: the rejection cue (POP-6); a drop: the `no-drop` cursor and no target highlight while dragging, then a message at the target ("Only .json files"; on touch the message is the cue). A rejection is announced (`Sw.Page.Announce`) on each attempt, except that the same input on the same element within 1 s is announced once (one rule for every rejection), and is never a toast; repeated attempts re-pulse but never stack messages. A shortcut that doesn't apply in the current context and has no control (Ctrl+S on a page without Save) is not an attempted action.
  - The reaction is measured from the input event's `timeStamp` to the first frame that shows the change (as the Event Timing API does), at the 75th percentile of at least 20 runs of each main interaction on the PRF-1 reference setup; the pressed state is applied at 0 ms. Example: a 5 s report download shows the button busy at once and a toast "Preparing report.xlsx…" until the file arrives.
- **UX-FBK-2 (MUST, owner) Busy buttons block repeats.** `F · auto` A button that starts async work ignores (absorbs, FBK-1) further clicks and Enter until the work ends, so the action can't run twice. **Busy is not disabled:** it keeps its label, colour and focus, shows `cursor: progress` on itself and sets `aria-busy="true"` (screen readers don't read it alone). It announces through `Sw.Page.Announce`: "Working…" only when the spinner appears (FBK-3), then the result once, by the button or by the result toast, never both. Exception: actions meant to be repeated that finish in under 100 ms (increment / decrement, add an empty row, a toggle).
- **UX-FBK-3 (MUST, owner) Working animation after 250 ms.** `F · auto` Work still running at 250 ms (200–300 ms accepted) shows a spinner on the button or area; shorter work shows none, so fast actions don't flicker. The button keeps its width (the spinner replaces the icon or overlays the label).
- **UX-FBK-4 (MUST) Long work shows progress and can be cancelled.** `F+P · manual` Work that can take more than 2 s shows progress (determinate when the amount is known, else what it waits for and the time so far; reserved space) and has Cancel when it can be cancelled. Progress values and elapsed time are never in a live region (`role="progressbar"` with `aria-valuenow`), but the progress text is part of the busy dialog's or button's description, so it can be read on demand; announced are the start ("Uploading report.xlsx"), phase changes, at most one update every 30 s, and the result. Work that goes on after the user leaves says so.
  - **The activity list** holds all background work (POP-6 "Continue in background"): a shell header button, also in the phone layout (never only in the menu; 44 × 44 px on touch), reachable with F6; it opens the list as a sheet in the phone layout. Its badge counts running and failed-not-opened items (not finished ones); with none it shows no badge; the button itself appears only once the session has activity (a job running, finished or failed and not removed) and goes when the list is empty, without moving the other tools of the top bar (LAY-1); a failure changes the badge (icon and colour, ACC-2); its accessible name says the counts ("Activity: 1 running, 1 failed"); count changes aren't announced on their own, a failure is announced once (`role="alert"`, from inside an open modal, POP-1). While the tab is hidden, a result toast waits until the tab is visible again (its timer starts then) and the tab title shows the result ("✓ Export done") until then.
  - Items, each one list item with its state in text: running (progress, Cancel), finished (a link to the result, kept for the session) or failed (the error, "Details", "Try again" with the original inputs; kept until opened). Server jobs come back after a reload and in other tabs of the same user; shell-level tasks end with the page (SAF-10 asks first). The result never depends on a toast (FBK-5); reopening the dialog or its opener while the job runs shows the running item, never a second start (FBK-2).
- **UX-FBK-5 (MUST) Every result is visible, in place first.** `F+P · manual` Success shows where the user acts (the row updated, the switch changed, a check mark on the button); a toast only when the result isn't visible there (a download, a background job (also kept in the activity list, FBK-4), a change on another page or behind a closed dialog), never a "Saved" toast after every toggle. Failure shows a clear error (UX-TXT-30) at the place of the action or as an error toast with "Details" and "Copy". Never fail silently or only in the console.
- **UX-FBK-6 (MUST) Loading, empty and error states.** `F+P · manual` Every area that loads data has a loading state (skeleton, or a spinner after 250 ms), an empty state that says what would be here and how to add it, and an error state with "Try again". They never change the size of the area (UX-LAY-1).
- **UX-FBK-7 (SHOULD) Live data updates in place**, with a short highlight of what changed, without moving rows under the pointer or focus (defer re-sorting until the pointer leaves, or keep the order and mark rows that would move). Screen readers get at most one polite summary per refresh ("3 rows updated"), never while the user types. `F+P · manual`
- **UX-FBK-8 (MUST) Toasts can be read and used by everyone.** `F · auto` Toasts don't cover actions (they lift above sticky bars and primary buttons), never take focus, and can be closed (on touch also by a swipe). They stay `5 s + 60 ms × characters`, at least 10 s with an action (Undo, SAF-5); the timer pauses while hovered or focused; errors stay until closed. They are announced with `role="status"` (`alert` for errors), including their action ("Deleted 3 rows. Undo available."). A toast action is also reachable another way for at least 60 s: in the page, or with F6, which also cycles to the toasts and the activity list (inside a modal too, POP-1). Important information is never only in a toast.
- **UX-FBK-9 (MUST) A lost connection is calm and loses nothing.** `F+P · auto` When the server can't be reached, one line says so ("Offline, retrying…", `role="status"`, announced once), not an error per failed call. Everything typed stays (fields untouched, drafts per SAF-11). Reads retry by themselves with back-off; when the server answers again the line says "Back online", the data refreshes and the line goes. A save in flight is never lost silently: it is resent when the connection returns if repeating it is safe, else the form keeps its values, the button leaves its busy state and says "Not saved: the connection was lost" with "Try again".

## 5. Motion

- **UX-MOT-1 (MUST, owner) Every visual change of a UI element is a transition** `F+P · auto` (interpolated over a theme duration token, a step change only when the token is 0): hover and pressed states, showing and hiding (menus, dialogs, tool tips, toasts, expanding sections), colour changes, selection, meter values. Exceptions: the pressed state and the focus ring appear at 0 ms (FBK-1, FOC-3); content changes (a new number, a replaced text) can't be interpolated and change in place or cross-fade. A theme switch cross-fades within `--sw-dur-2` without a flash (instant under reduced motion).
- **UX-MOT-2 (MUST, owner) Durations and distances come from the theme.** `F+P · lint:unknown-token, manual` Never hard-code a duration, delay, easing or slide distance: use `--sw-dur-1` (hover, small state changes), `--sw-dur-2` (menus, switches, tool tips), `--sw-dur-3` (dialogs, drawers, sheets), `--sw-ease` and the distance tokens. Each theme sets its own values, some zero (a "no animation" theme, Hacker); the result must still be correct (no state that depends on a transition ending; `transitionend` only with a fallback timer).
- **UX-MOT-3 (MUST) Reduced motion is respected.** `F · auto` With `prefers-reduced-motion: reduce` durations become near zero (the framework sets 1 ms) and nothing slides, zooms or parallaxes.
- **UX-MOT-4 (MUST) Animate only `opacity`, `transform` and colours.** `F+P · manual` Never width, height, top, left or margins. One exception: a section the user expands or collapses may animate `grid-template-rows` (`0fr` ↔ `1fr`).
- **UX-MOT-5 (MUST) Motion never delays input.** `F · auto` The user can act during an animation.
- **UX-MOT-6 (MUST) No endless motion** except a spinner or skeleton while work runs and an explicit "live" indicator; no auto-playing carousels, no blinking. `F+P · manual`
- **UX-MOT-7 (MUST) Faded out is gone.** `F+P · auto` Content faded to `opacity: 0` is also hidden from focus and screen readers (`visibility: hidden`, `inert` or removed) once the fade ends.

## 6. Layout stability

The target is **zero layout shift** after the first paint (Cumulative Layout Shift 0 in a recorded reload): the user aims at a button and the page must not move under the pointer.

- **UX-LAY-1 (MUST, owner) Reserve the space.** `F+P · auto` An element's final size is known before its content arrives: images, icons, iframes, charts, avatars and media have explicit sizes or an `aspect-ratio`; lists and tables reserve their height (skeleton rows, a fixed frame); badges and counters have room before their first value; error and hint lines under fields have reserved space or appear without pushing neighbours.
- **UX-LAY-2 (MUST, owner) Elements never grow when their assets are done.** `F+P · auto` Loading an image, a font, an icon set or data never makes an element bigger or moves its neighbours.
- **UX-LAY-3 (MUST, owner) Async media fade in.** `F+P · auto` Images, iframes, embedded pages and charts that load asynchronously are invisible while loading (the reserved box shows a skeleton placeholder with `aria-busy`) and fade in with `--sw-dur-2` when complete (`Sw.FadeSrc`); a failed load shows a small broken state in the same box, not the browser's broken image icon.
- **UX-LAY-4 (MUST, owner) Bars stay put.** `F · auto` Sticky headers, toolbars and table bars never jump when content or counts change or while paging: the table bar (pager, count) is pinned to the bottom, Next then Back is the same mouse position. Updating numbers use tabular figures and a minimum width.
- **UX-LAY-5 (MUST) No content inserted above what the user reads**, unless asked (new log lines are added without moving the view, or wait behind a "3 new" button). `F+P · manual`
- **UX-LAY-6 (MUST) Fonts don't shift the layout.** Local fonts only (no web font services), `font-display` that avoids a visible swap, fallback metrics that match. `F · lint:design-font, lint:external-resource`
- **UX-LAY-7 (MUST) Scrollbars don't shift content** (`scrollbar-gutter: stable` on containers that toggle between scrolling and not). `F+P · auto`
- **UX-LAY-8 (MUST) Responsive from 320 px to 4K.** `F+P · auto` Pages work from 320 CSS px wide to 2560 px and 4K, portrait and landscape, at 100–400 % zoom; no horizontal page scroll (only inside wide tables and code); no text cut off without an ellipsis and a tool tip with the full text.
- **UX-LAY-9 (MUST, owner) No layout shift on input: reserve the space, change only the opacity.** `F+P · auto` Nothing moves while the user types, picks or leaves a field: everything a form, dialog or page shows or hides in reaction to input (validation messages, hints, password rules and policies, a status or hint next to a button, conditional help, a leaked password note, the rows of a collapsed or expanded menu) has its space before the first key, as large as its longest content, and only its opacity (visibility) changes; never `display: none` / insert / remove for such content, never a bolder or larger text for a state. A message longer than its reserved space (a server's answer) may grow its line once, then keeps that height. Measured with a `layout-shift` observer that counts `hadRecentInput` entries too: 0 while typing. Framework: `Sw.Reserve` (lines, stacks with sizer copies), the reserved message lines of the controls (`Messages` option), the developer warnings and the dialog self-test (ui/README "No layout shift on input").

## 7. Tool tips, labels and help

- **UX-TIP-1 (MUST, owner) Every action has a tool tip that says what will happen.** `F+P · lint:a11y-name, manual` The tool tip adds what the label doesn't say: the target, the consequence or the shortcut. Bad: Save → "Save". Good: "Save changes to appsettings.json (Ctrl+S)", "Delete the selected rows (asks first)", "Open the process in a new window". A menu item whose label names both the verb and the object ("Delete row") needs a tool tip only for a consequence or a shortcut.
- **UX-TIP-2 (MUST) Names and descriptions for assistive technology.** `F · lint:a11y-name` The accessible name is the visible label, or an `aria-label` from a translated string for icon-only controls; the tool tip is the description and never repeats the name (a screen reader reads both on every Tab, so keep it short). In lists and grids repeated controls get unique names ("Copy the API key of MailService", not 20 × "Copy"), a description that is the same on every row is exposed once (on the grid or the column header), and shortcuts are also given as `aria-keyshortcuts`.
- **UX-TIP-4 (MUST) Tool tips are not the only place for essential information.** `F+P · manual` On touch the main actions of a page have visible labels (text, or icon and text); icon-only buttons show their tool tip on a long press (`Sw.Hint`, INP-5); other explanations sit behind an info button. Validation errors, warnings and required hints are inline.
- **UX-TIP-5 (MUST) Tool tips are reachable** by keyboard focus (shown within 1 s) as well as by hover, stay until the pointer leaves the element and the tool tip, focus moves or Escape is pressed (the first Escape goes to an open tool tip, before any field list, edit or pop-up, POP-3) [1.4.13], are placed inside the viewport (`Sw.Place`, also at 400 % zoom) and don't cover the element they describe (a SysWeaver rule beyond 1.4.13). `F · auto`
- **UX-TIP-6 (MUST) Truncated text shows its full value in a tool tip** (cells, titles, breadcrumbs; LAY-8), also on keyboard focus (TIP-5); the full text stays in the accessible text, never only in the tool tip. `F · auto`
- **UX-TIP-7 (MUST, owner) No repeated helper text.** `P · manual` *Why: every visible text costs effort to read or to ignore.* A hint, explanation or instruction that would appear on every card, row or item appears once (in the header, an empty state or a tool tip), or not at all.
  - Bad: every card of a service list ends with "Click to open the details". Good: the cards look clickable (cursor, hover; INP-10 / 11) and the tool tip says "Open the details of MailService".
- **UX-TIP-8 (SHOULD, owner) A self-explaining UI over instructions; help that goes away.** `F+P · manual` Prefer a UI that is clear without help, even if a new task takes a little longer to learn; once learned, permanent help text is a distraction. Keep help minimal. Where help is needed, prefer help that disappears once the action is learned: shown until the user has completed the action 3 times (with any input) or dismissed it, remembered per user (per browser when nobody is signed in).
  - A hint names a path for every input ("Drag a column header, or use its menu → Move left / right"), sits next to its control in reading order (`aria-describedby`), never disappears while focused or being read, and leaves no layout shift.
  - Gone hints stay retrievable behind the page's help / info button. (There is no framework hint component and no shell "Show hints again" setting: removed 2026-10-26, OWN3-Shell-4.)
  - Not usage help, so never faded: instructions a field or control needs to be used correctly (formats, units, limits, what a required choice means; labels or instructions under [3.3.2]), reminders needed every time such as the password policy on sign-in (FRM-4), warnings about consequences (SAF-2), and empty-state guidance (FBK-6), which goes away by itself. Only help on how to operate the UI ("Drag a column header …") may fade.

## 8. Text and localization

All text a user can read must be translatable, and no layout may depend on a text's length. The server translates `.js` and `.html` files before serving them (`SysWeaver.FileTranslation`: `JsTranslation.cs`, `HtmlTranslation.cs`); [Appendix A](#appendix-a-how-the-translators-work) explains how. CSS is not translated.

### 8.1 JavaScript: `_T`, `_TF`, `_TH`, `_TFH`

| Function | Use | Example |
|---|---|---|
| `_TF(text, context)` | Fixed text, no placeholders (most labels, titles, tool tips) | `_TF("Refresh", "Button that reloads the list of services")` |
| `_T(format, arg0, …, context)` | Text with placeholders `{0}`, `{1}` … | `_T("Deleted {0} of {1} files", done, total, "Toast after a delete. {0}: files deleted, ex: 3; {1}: files selected, ex: 5")` |
| `_TFH(text, context)` | Like `_TF`, the result goes into `innerHTML` (the server makes the translation HTML safe) | |
| `_TH(format, args…, context)` | Like `_T`, for HTML; values can be emphasised with `Sw.I18n.ArgAsHtml(value)` | `_TH("Click {0} to keep it", Sw.I18n.ArgAsHtml(_TF("Save", "…")), "…")` |

- **UX-TXT-1 (MUST, owner) Every user visible string goes through one of the four functions** `P · lint:tr-untranslated`: labels, titles, tool tips, `aria-label`s, placeholders, toasts, dialog texts, errors, empty states, units shown as words, menu items. Not translated: data from the server, code, identifiers, log content, numbers and dates (`Sw.Format`, UX-TXT-20).
- **UX-TXT-2 (MUST) The first argument is a string literal** (`'…'` or `"…"`) at the call site, never a variable, a concatenation or a template literal: the translator only sees literals. `P · lint:tr-not-literal`
- **UX-TXT-3 (MUST) The names are permanent and reserved.** `P · lint:tr-in-text, lint:tr-identifier-suffix, lint:tr-alias` Never write `_T(`, `_TF(`, `_TH(`, `_TFH(` anywhere but in a real call (not in comments, strings or HTML), never call an identifier that ends with one of them (`MAX_T(`), never rename or alias them (`const t = _T`).
- **UX-TXT-4 (MUST) `_TF` without placeholders, `_T` only with placeholders.** `P · lint:tr-format` `_TF("Hello {0}", name)` is formatted only when the server translates the file and shows `{0}` otherwise; `_T("Hi {0}")` without an argument shows `{0}`.
- **UX-TXT-5 (MUST) The `H` variants only for `innerHTML`.** Prefer text APIs (`textContent`, `Sw.el(…, { text })`) with `_T` / `_TF`. `P · manual`
- **UX-TXT-6 (MUST) Whole sentences with placeholders, never concatenation.** `P · manual` Write `_T("Deleted {0} of {1} files", done, total, "…")`, never `_TF("Deleted") + " " + done + …` (word order differs between languages). No plurals by adding "s": write a sentence that works for one and many ("Files: {0}") or provide both forms.
- **UX-TXT-8 (MUST, owner) A high quality context for every string.** `P · manual` The translator (a person or an LLM) sees only the text and the context, never the page. The context says where the text appears (button, menu item, column header, tool tip, dialog title, error toast, placeholder) and on which page; what it does or means; every placeholder (what `{0}` is, its type and an example); limits and tone when they matter ("very short, fits a 6 rem button", "a verb in the imperative").
  - Example: `_T("Kill {0} ({1})?", name, pid, "Title of the confirmation dialog before stopping a process. {0} is the process name, ex: 'dotnet'; {1} is its process id, ex: 4711.")`.
- **UX-TXT-9 (MUST) Same text, different meaning = different context.** "Open" (a button) and "Open" (a status) get different contexts, so they get separate translations. `P · manual`

### 8.2 HTML

The HTML translator translates every text node with a letter in it and the attributes `title`, `placeholder`, `alt` and `aria-label`; inline `<script>` is translated like a `.js` file; `<style>` is not. It writes an automatic context (where the text is) and adds the nearest `data-translation_context` attributes (what it means). Details in Appendix A.

- **UX-TXT-10 (MUST) Keep a sentence in one text node.** `P · manual` Inline markup splits a sentence into units translated alone (`Click <b>Save</b> to keep it` becomes three fragments). Rephrase, or build it in JS with one `_TH` call (see the 8.1 example).
- **UX-TXT-11 (MUST) Add `data-translation_context`** to every element whose text is short or ambiguous (single words, labels, buttons), and once on the page or section to say what the page is. `P · manual`

  ```html
  <section data-translation_context="Sign in page of an administration console">
    <button title="Sign in with a passkey" data-translation_context="Button that signs the user in with a passkey (WebAuthn)">Passkey</button>
  </section>
  ```
- **UX-TXT-12 (MUST) Mark non-translatable text** (code, product names, sample data) with `translate="no"` (lower case); text in another language that is read aloud also gets `lang` [3.1.2]. `P · manual`
- **UX-TXT-13 (MUST) Text in other attributes is set from JS.** `aria-description`, `aria-valuetext`, `value`, `content` and `data-*` are served as written: set user visible texts in them with `_TF`. `title`, `placeholder`, `alt` and `aria-label` may be written in the HTML. `P · manual`

### 8.3 CSS: no translation (not supported)

CSS translation is not implemented (`<style>` and `.css` files are served as written).

- **UX-TXT-15 (MUST, owner) No user visible words in CSS.** `content:` holds only symbols that need no translation (icons, "…", bullets, separators, an empty string), never words like "New" or "(required)". `P · manual`
- **UX-TXT-16 (MUST) Don't localize through CSS.** Standard ellipsis, `quotes: auto` with the page `lang` (set by the translator), standard list markers or symbols. `P · manual`

### 8.4 Layout for any language

- **UX-TXT-17 (MUST, owner) Never assume a text width.** `P · manual` Translations are often 30–50 % longer than English (short labels can double). Buttons, tabs, menus, columns, badges and headers grow or wrap; no fixed widths for text, no `white-space: nowrap` without an ellipsis and a tool tip, no text in images.
- **UX-TXT-18 (MUST) Test long text** with a pseudo-translation or a long language (German, Finnish) at 390 px width. `P · manual`
- **UX-TXT-19 (SHOULD) Be ready for right-to-left**: logical CSS properties (`margin-inline-start`, `inset-inline-end`, `text-align: start`). `P · manual`
- **UX-TXT-20 (MUST) Format numbers, dates, times, sizes and durations with `Sw.Format`**; UI times are the viewer's local time, any other clock is labelled with its zone (core README "Times"). `P · manual`

### 8.5 Wording

- **UX-TXT-25 (MUST) Plain, short and specific.** Sentence case ("Delete account"), verbs on buttons, no jargon on non-technical pages, no internal ids or class names in UI text. `P · manual`
- **UX-TXT-26 (MUST) Consistent terms**: one name per concept (always "sign in", never sometimes "log in"); page titles match their menu names. `P · manual`
- **UX-TXT-30 (MUST) Errors say what happened, why and what to do**, in user words ("The file is too large (12 MB). The limit is 10 MB."), with technical details behind "Details" / "Copy". Never a raw "404 - Not Found" or a stack trace. `F+P · manual`

## 9. Data safety

### Destructive operations

- **UX-SAF-1 (MUST, owner) Confirm destructive operations.** `F+P · lint:design-confirm, manual` Any destructive action (delete, remove, kill, reboot, end session, revoke, reset, overwrite, send to other people) asks first. Exempt only: removing something the user created and hasn't saved (a line just typed, a restored draft, a filter chip), and actions whose result stays reversible after their Undo window (SAF-5).
- **UX-SAF-2 (MUST) The confirmation names the action, the target and the consequence**: title "Delete 3 users?", text "Their accounts, settings and sessions are removed. This can't be undone.", buttons "Delete users" (danger) and "Cancel". Use `Sw.Cells.ConfirmDanger` (or `Sw.Dialog.Confirm(title, text, verb, { Danger: true })`, `Sw.Dialog.DangerTitle`), never "Are you sure?" alone, never "OK / Cancel". `F+P · lint:design-confirm`
- **UX-SAF-3 (MUST) The safe choice has the focus** (Cancel); the destructive button is never the Enter default; in menus destructive items are last, separated and never focused first. `F · auto`
- **UX-SAF-4 (MUST) Type to confirm** for irreversible actions that affect other users' data or access, a production system, or all items of a kind (delete an account, drop all data, reboot a production server): the user types the target's name to enable the button (`ConfirmDanger` option `Confirm`). `F+P · manual`
- **UX-SAF-5 (SHOULD) Prefer Undo where the result stays reversible.** `P · manual` An action whose result can still be reverted after the Undo window (archive, hide, move, a delete kept in a recycle bin) runs at once and offers Undo for at least 10 s in the toast (FBK-8) and 60 s in the page, instead of asking first: too many confirmations teach users to click through them. A delete that becomes final when its Undo expires is destructive: it is confirmed (SAF-1) and may offer Undo as well.
- **UX-SAF-6 (MUST) Say "can't be undone" only when it is true.** `P · manual` (`ConfirmDanger` adds "This cannot be undone." by default: pass `Warning: ""` or a correct text when it can be undone.)
- **UX-SAF-7 (MUST) The server decides too.** `F+P · manual` A UI confirmation is not a security measure: destructive APIs check authorization and, where it matters, a token or code. Actions the user may not run are hidden or disabled with a reason before the first click (`Sw.Access`), and a refused request says "Your role doesn't allow this", not a raw 403.

### Unsaved edits and drafts

- **UX-SAF-10 (MUST, owner; opt in since 1.7.0) Leaving a page with unsaved edits warns where the page opts in.** `F+P · manual` The original framework never asked before leaving, and parity with the original wins (owner direction, 1.7.0): a page asks only where the original page asked (its own `beforeunload`) or the owner asked for it; the framework marks nothing dirty by itself (the Sw controls, forms, editors and dialogs opt in with `Dirty`). While a page that opted in is dirty, in-app navigation (menu, links, Back in the shell) asks "Leave without saving? Your changes to X are lost." ("Leave" / "Stay"); closing or reloading the tab uses the browser's `beforeunload` prompt. The page shows that it is dirty (a dot on the tab or title, an enabled Save). Work that would stop when the page is left asks the same way ("Leave? The export stops.").
- **UX-SAF-11 (MUST, owner) Uncommitted text survives a refresh.** `F+P · auto`
  - Text typed but not sent or saved (chat input, a comment, a message, a long form) is stored as a draft in local storage while typing (debounced 500 ms, 300–1000 ms accepted), restored on the next load, and cleared when sent, saved or discarded. A restored draft does not make its form dirty (1.7.0, parity: the original never asked; a form that opted into SAF-10 may opt in here too).
  - Keyed per site, user and context (ex: per chat room), with a common per-user key prefix; at most 64 KB per draft; expires after 7 days. An explicit Sign out clears all drafts of the user (shared computers); a session time-out or a forced sign out (ACC-7) keeps them.
  - Never drafted: `type="password"`, `autocomplete="one-time-code"`, `current-password`, `new-password`, and fields marked `data-sw-nodraft` (secrets).
  - A restored draft is announced: an inline line "Draft restored (saved 10:42)", with the date when it isn't today, and a "Discard draft" button next to the field, also read through `role="status"`. Discarding offers Undo (SAF-5).
- **UX-SAF-12 (MUST) Restore view state on Back.** After Back (browser or shell) the scroll position, the open tab, filters, sort and page size come back (`Sw.History`); after a reload they SHOULD come back too. `F+P · auto`

## 10. Forms and validation

- **UX-FRM-1 (MUST) Every field has a visible label** (not only a placeholder), linked to the field; placeholders show examples, not instructions. `F+P · lint:a11y-name, auto`
- **UX-FRM-2 (MUST) Required fields are marked** (a marker and `aria-required`); optional ones may say "(optional)". `F · auto`
- **UX-FRM-3 (MUST) Validate inline and once.** `F · lint:design-error-twice, auto` Messages appear under the field (`aria-describedby`, `aria-invalid`) after the user leaves the field or submits, never while still typing the first time; they disappear as soon as the value is valid (also after a value set from code). An error is shown once (not as a field message and a toast). On submit focus moves to the first invalid field.
- **UX-FRM-4 (MUST) Rules are visible before the error.** Password rules, formats and limits show next to the field from the start (and tick off as they are met). Policy rules stay visible on sign-in too, as a reminder. `F+P · manual`
- **UX-FRM-5 (MUST) Never lose input** on an error: the form keeps every value; a server error shows at the field it concerns or at the top of the form. `F+P · manual`
- **UX-FRM-6 (MUST) Right input types and attributes**: `type="email"`, `inputmode="numeric"`, `autocomplete` on every field that collects the user's own data (`username`, `email`, `new-password`, `one-time-code` …) [1.3.5], `spellcheck="false"` for codes. `P · manual`
- **UX-FRM-7 (SHOULD) Don't disable submit to signal errors**; let the user submit and show what is missing. `P · manual`
- **UX-FRM-8 (MUST) Read-only is really read-only** and looks like text, not like a disabled input; nothing can change the value (typing, paste, drop, drag, menus). `F · auto`
- **UX-FRM-9 (MUST) No redundant entry** [3.3.7]: information the user already gave in the same process is filled in or offered, not asked again (except to confirm a new password). `P · manual`
- **UX-FRM-10 (MUST) Accessible sign in** [3.3.8]: no puzzle or memory test; paste and password managers work in every credential field; passkeys where offered. `F+P · manual`

## 11. Lists, tables and navigation

The shared table (`explore/table.*`) implements these; pages that build their own lists follow them too.

- **UX-LST-2 (MUST) Row actions are always visible and don't cover data.** Every row shows its actions at rest, on mouse and touch screens alike (quiet styling such as ghost buttons in the secondary text colour is fine; hidden until hover or focus, `opacity: 0`, `visibility: hidden` or a 0 px column is not), in their own column or a row menu button, never over a value. They are reachable by keyboard (Tab, the cell menu, Shift+F10). *Why: in a list of hundreds of rows an action that only appears under the pointer can't be found (CMP-B3), and a hover-only column of 0 px could not be clicked at all (CMP-B1).* `F · auto`
- **UX-LST-3 (MUST) Visible sorting.** Sorting is visible (an arrow on the header, `aria-sort` for screen readers), and the user's own order wins over the default. Data tables keep the original order rules (1.5.0, owner: no gap to the old behaviour): a column sorts descending first only when the server says so (`SortedDesc`), and a click on another column makes it the primary key and keeps the earlier ones (up to 3). `F · auto`
- **UX-LST-4 (MUST) Clicks don't change.** A plain click on a cell never changes anything (no edit, no toggle, no row action without its button). A value cell that the original copied on a click copies it (1.6.0, as the original `copyOnClick`; UX-INP-31); copy is also Ctrl+C on the focused cell and the cell menu. `F · auto`
- **UX-LST-5 (MUST) Honest counts.** When the server doesn't count every row, say "more follow", not a wrong total; paged tables set `aria-rowcount` (`-1` when unknown). `F · manual`
- **UX-LST-6 (MUST) Oriented navigation.** The page title matches the menu name, the breadcrumb shows where the page is, Back works, links are real links (new tab with Ctrl / middle click), `Sw.Page.Navigate` opens in the same tab unless asked. `F+P · lint:design-navigate, manual`
- **UX-LST-7 (MUST) Search.** All words must match (AND); lists and pickers update while typing (debounced 300 ms, no Enter needed), data tables apply the search on Enter, leaving the field or Clear, like the original table (1.5.0, owner: no gap to the old behaviour; no server request per pause) and the previous results stay until the new ones arrive (no flash of the empty state); the search text stays visible with a clear (×) button; the result count updates (one polite summary, FBK-7). `F · auto`

## 12. Accessibility

Target: **WCAG 2.2 level AA** for every page. A page conforms only when it breaks no rule and every [Framework support](#framework-support) row it relies on is Supported; filing a gap once against the framework routes the finding, it is not a waiver, and an accessibility statement lists such gaps as known failures. Rules elsewhere that implement it: INP-1, 2, 3, 12, 20, 24, 25; POP-1–7; FOC-*; FBK-1, 2, 4, 8; TIP-2, 5, 6, 8; TXT-12; SAF-11; FRM-*.

- **UX-ACC-1 (MUST) Contrast** [1.4.3, 1.4.11]: text 4.5:1 (large text 3:1); icons, control borders and focus rings 3:1, in every theme (light, dark, Pro, Application, Hacker, custom). `F+P · auto`
- **UX-ACC-2 (MUST) Never colour alone** [1.4.1, 1.3.3]: status has an icon and a word as well as a colour; charts have labels or patterns and a table view; instructions and hints never rely on colour, shape, size, position or sound alone ("the green button", "on the right"): they name the control by its label. `F+P · manual`
- **UX-ACC-3 (MUST) Semantics** [1.3.1, 4.1.2]: landmarks (`header`, `nav`, `main`), one `h1` per page, headings in order, lists as lists, tables with header cells, ARIA roles only where no native element exists. `F+P · auto`
- **UX-ACC-4 (MUST) Announce changes** [4.1.3]: toasts and status lines use `role="status"` (`alert` for errors); busy controls announce (FBK-2); live counters don't spam the screen reader. `F+P · manual`
- **UX-ACC-5 (MUST) Names for everything** [1.1.1, 4.1.2]: every control, image (`alt`, empty for decoration), icon button and region. `F+P · lint:a11y-name`
- **UX-ACC-6 (MUST) Reflow and text spacing** [1.4.4, 1.4.10, 1.4.12]: at 400 % zoom / 320 CSS px wide content reflows with no two-way scrolling, and dialogs, menus, tool tips and toasts stay inside the viewport; user text spacing doesn't hide or overlap content. `F+P · auto`
- **UX-ACC-7 (MUST) Time limits** [2.2.1]: a session time-out warns at least 20 s before (`role="alert"`) and is extended with one key or click ("Stay signed in"), also while a dialog is open (it opens above it, POP-5); auto-refresh can be paused. `F · manual`
- **UX-ACC-8 (MUST) Forced colors** (Windows contrast themes): icons use `currentColor`, state is never shown by a background colour alone, focus rings are outlines, and the page is checked under a contrast theme. `F+P · manual`
- **UX-ACC-9 (MUST) Consistent help** [3.2.6]: help and contact links sit in the same place on every page (the shell). `F · manual`
- **UX-ACC-10 (MUST) Label in name** [2.5.3]: a control with visible text has an accessible name that starts with that text (no `aria-label` that turns "Save" into "Store configuration"); icon-only controls get a short, speakable name, so "Click Refresh" works in voice control. `F+P · lint:a11y-name, manual`
- **UX-ACC-11 (MUST) No surprise on focus or input** [3.2.1, 3.2.2]. `F+P · manual` Moving focus to a control never opens a pop-up that takes focus, navigates or submits. Changing a select, radio, checkbox or field value never navigates, submits or moves focus unless the control says so beforehand (a "Go" button, a label "Opens the selected page"). Live filters and search (LST-7) may update results in place but never move focus.
- **UX-ACC-12 (MUST) Media alternatives** [1.2.1, 1.2.2, 1.2.3, 1.2.5]: embedded video with speech has captions, and an audio description where the picture shows what the speech doesn't say; audio only has a transcript. Admin pages rarely embed media. `P · manual`

## 13. Performance as perceived

- **UX-PRF-1 (SHOULD)** On the reference setup (server and browser on the same LAN, Chrome desktop, no throttling, warm server, cold browser cache) a page shows first content within 1 s; interactions answer within 100 ms (measured as FBK-1); anything longer shows feedback (section 4). `F+P · auto`
- **UX-PRF-2 (MUST)** No main thread task over 50 ms in event handlers; large lists are paged or virtualized (a table renders at most a page of rows). `F+P · auto`
- **UX-PRF-3 (MUST)** Pages work from the server alone: no CDN, no external fonts, scripts or images (map tiles only when the app opts in). `F · lint:external-resource`
- **UX-PRF-4 (SHOULD)** Repeated navigation doesn't leak memory (listeners, timers and observers are removed when a component is destroyed). `F+P · auto`

## 14. Security in the UI

- **UX-SEC-1 (MUST)** Secrets (passwords, API keys, tokens) are masked by default with a "Show" toggle, copied without showing when possible (UX-INP-31), never put in URLs or local storage. `F+P · manual`
- **UX-SEC-2 (MUST)** User content is shown as text (or sanitized HTML from the server), never inserted as raw HTML. `F+P · manual`
- **UX-SEC-3 (MUST, owner) Sign in and sign out reload the whole page.** After a sign in the application loads again (the menus, the user and the data of the new user); after a sign out (in this tab, in another tab, or a session that ended on the server) nothing of the signed in user stays on screen, not even for a moment: no menu, no user data, no page content. No dialog over the old page. A short "You are signed out" notice on the reloaded page is fine; it closes by itself and shows once per sign out, never again on a later reload or check. The password checks of the sign in page send the same requests as before (the user's password policy on every change of the user id; the password leak check). `F · auto`

## 15. Phones and touch

- **UX-MOB-1 (MUST) The on-screen keyboard never covers the field being typed in**; the field and its error line scroll into the visible viewport, and sticky bars move above the keyboard. `F · auto`
- **UX-MOB-2 (MUST) Sticky bars take at most 25 % of the viewport height together** in the phone layout. `F+P · auto`
- **UX-MOB-3 (MUST) Back closes the top pop-up first.** On every device the browser's Back (phone gesture, browser button, mouse back button) closes the top sheet, dialog or menu, not the page; in a dirty or busy dialog it is a close attempt (POP-6). `F · auto`
- **UX-MOB-4 (SHOULD) Main actions are within thumb reach**: in the phone layout primary actions of a page or sheet sit at the bottom (a bottom bar or the sheet's foot). `F+P · manual`
- **UX-MOB-5 (MUST) Don't fight the platform**: the theme follows the device's light / dark setting unless the user chose one; inner scrollers use `overscroll-behavior: contain`, so pull-to-refresh and swipe-back only act on the page. `F · manual`

## Page review checklist

**Gate first:** `SwWeb check <srcWeb> --strict --design` = 0 findings (it covers the `lint:` rules above), and 0 console errors. Rate each finding Blocker / Major / Minor and route framework gaps as in [How to read and audit](#how-to-read-and-audit).

**Full pass (every page that is new or changed in the release, and every page at least once a year):** 1920×1080 with mouse and keyboard, 390×844 with touch, light and dark theme; NVDA + Chrome on the page's main task (open, act, a dialog, a form) in browse and focus mode (Tab and quick keys: the ring follows), also in Firefox, and VoiceOver + macOS Safari for item 6; keyboard only, and mouse then keyboard (click, then Tab: the ring appears).

**Spot pass (each release, 10 % of the other pages, at least 3):** 2560×1440, 1366×768, 844×390, 400 % zoom (320 CSS px, and 1280×720 at 400 % = 320×180), the other themes, a Windows contrast theme, a pseudo-translation, VoiceOver and Speak Selection on iOS, Safari on macOS with Option+Tab, mouse clicks only without dragging, the network cut off during a save.

1. **Clicks**: a modifier click never acts and moves the focus (Ctrl+click a button: the ring shows in Chrome, Firefox and Safari; Shift+click extends text; item selection only in multi-select lists; link gestures work); menu buttons open on a pure right click, Menu key and Shift+F10; nothing on hover alone. (INP-1–8)
2. **Cursor and hover** on every interactive element; disabled controls look disabled, stay focusable and say why. (INP-10–12)
3. **Keyboard only**: every function reachable; logical tab order; Escape, Enter, arrows work; no single-key shortcut in text fields. (INP-20–23)
4. **Touch only**: every function reachable; targets ≥ 44 px; long press for menus; no hover-only actions; main actions labelled and, at 390×844, at the bottom within thumb reach. (INP-5, 24, TIP-4, MOB-*)
5. **Selection and copy**: chrome isn't selectable, content and sentence text are (select a dialog message and an error with Speak Selection); ids, keys and error details copy in one step (a click on a value copies it, as the original). (INP-30, 31)
6. **Pop-ups**: block everything behind; outside click closes without acting; the POP-6 table is tested once per dialog component (`Sw.Dialog`, sheets, `Sw.Dialog.Working`) when its framework row is Supported, a page audit checks that the page marks its dialogs dirty / busy and offers the right ways out; the rejection, the 10 s options and "Continuing in the background" heard with NVDA and VoiceOver (macOS Safari), "click Cancel" works in Voice Access; focus in and back; titled, verb buttons, movable / resizable / remembered. (POP-*)
7. **Focus**: best initial focus on the page and in every dialog / menu; never lost to the body; the browser's `:focus-visible` ring on keyboard focus, visible, unclipped, 3:1 and kept in a contrast theme; current item visible after a click too. (FOC-*)
8. **Feedback**: every action reacts within 100 ms, a refused one with the reason; busy buttons absorb repeats; spinner after 250 ms; progress without chatter; results in place; loading / empty / error states; toasts readable; a lost connection keeps input and saves. (FBK-*)
9. **Motion**: every visual change transitions with theme tokens; nothing hard-coded; reduced motion works; only opacity, transform and colours animate (plus `grid-template-rows` for expanding sections). (MOT-*)
10. **Layout stability**: no shift while loading (record a reload) and none while typing (type, blur and fix every field with a layout-shift observer that counts entries after input too: 0; LAY-9); media fade in; bars and counters still; no horizontal page scroll; long text wraps or ellipsizes with a tool tip. (LAY-*)
11. **Tool tips and help**: every action's tool tip adds the target, consequence or shortcut; no helper text repeated on cards or rows (on screen or in speech); no permanent usage help that a self-explaining UI or a fading hint could replace. (TIP-*)
12. **Text**: every string translated with a good context; sentences in one text node; no words in CSS; layout survives a pseudo-translation; `Sw.Format`; plain, consistent wording; errors say what to do. (TXT-*)
13. **Safety**: destructive actions confirmed with target and consequence (Undo instead only when the result stays reversible), Cancel focused; unsaved edits warn on leaving; drafts survive a reload and say so. (SAF-*)
14. **Forms**: labels, required markers, inline validation once, rules visible early, input kept on errors, paste works in credentials. (FRM-*)
15. **Accessibility**: contrast in every theme, not colour alone, no "the green button" / "on the right" instructions, landmarks and headings, announcements, names (label in name), reflow at 400 %, no navigation or submit on focus or value change. (ACC-*)

## Appendix A: how the translators work

Both translators are in `SysWeaver.FileTranslation` (`ExtensionHandlers/`). They turn a served file into a language template: every translation unit becomes a variable that is filled with the text for the session's language, together with its context (for the person or LLM that translates it).

### JavaScript (`JsTranslation.cs`)

- It scans for `_T`, `_TF`, `_TH` or `_TFH`, optional white space, `(` and a quoted literal (`"…"` or `'…'`); a backtick, a variable or anything else is not a call it sees (hence UX-TXT-2). It matches the names at the end of any identifier too (`MAX_T("x")`), hence UX-TXT-3.
- The first literal is the text. If the last argument is a quoted literal that follows a comma, it is the **context** and is removed from the served code (`x + "s"` as the last argument is not a context).
- A call with no other arguments is replaced by the translated string literal (no runtime call). A call with arguments becomes `_T(<translated text>, args…)`, formatted at run time, also for `_TF` (so `_TF` with arguments formats only on a translated site: UX-TXT-4).
- `_TH` / `_TFH` make the translated text HTML safe. Text without a letter is not translated.
- `core/i18n.js` holds the runtime fallbacks (no translator configured, or a call that still has arguments): `_T` / `_TH` format, `_TF` / `_TFH` return the text.
- **Placeholders** (`Sw.I18n.FormatArgs`): `{0}` is argument 0; `{_0}` lower-cases the value, `{^0}` upper-cases it, `{$0}` lower-cases it unless it starts the text. An undefined argument leaves the placeholder visible (a bug). A function argument (`Sw.I18n.ArgAsHtml`) is called to produce HTML.

### HTML (`HtmlTranslation.cs`)

It parses every served `.html` / `.htm` file (HtmlAgilityPack) and walks the tree:

- **Text nodes.** Every text node with at least one letter is one unit. Leading and trailing white space stays outside the unit; HTML entities are decoded; text that is already a template variable (`${…}`) is skipped. Inline markup splits a sentence into several units (UX-TXT-10).
- **Attributes.** `title`, `placeholder`, `alt` and `aria-label` are translated (same rules). The context of an `aria-label` tells the translator it is not shown but read aloud as the element's name. Other attributes (`aria-description`, `aria-valuetext`, `value`, `content`, `data-*`, …) are served as written (UX-TXT-13).
- **`<script>`** content is translated like a `.js` file. **`<style>`** is not processed (the CSS handler is a placeholder), and `.css` files have no handler (section 8.3).
- **Automatic context.** For a text node: "the content of an individual HTML text node on a `<element>` element", plus the surrounding text: the translator goes up to the first ancestor whose text is long enough and quotes up to max(3 × the unit's length, 10) characters on each side, cut at word boundaries, with the unit marked `>>text<<`. For an attribute: the attribute and the element name. This says *where* the text is, not what it means.
- **`data-translation_context`.** Starting at the text's element (the attribute's element), the translator walks up and takes the nearest `data-translation_context`, then the next one above that (at most 2, nearest first), and puts them before the automatic context. The attribute is removed from every served page.
- **`translate="no"`.** An element with `translate="no"` (lower case) is skipped with everything inside it, its attributes included; the attribute is removed when the page is translated.
- **Language.** When translating, `<html lang>` is set to the session language. When browser translation is not allowed for the site, `<body>` and `<head>` get `translate="no"` (and `<body>` the class `notranslate`), and `<meta name="google" content="notranslate">` is added, so browser translators don't translate the page a second time.
