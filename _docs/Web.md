## Packaging and serving

- Every project that ships web content has a `srcWeb/` folder. At build time `Compress.exe` Brotli-compresses it into `web/`, and the result is embedded in the assembly. Files are served at their path relative to `srcWeb/`, from the server root, e.g. `common/common.js`.
- **Served folders are merged across projects.** The URL namespace is shared, so several projects can contribute to the same folder:
  - `auth/` gets files from SysWeaver.Auth.Core, MicroService.Auth, MicroService.PassKey and MicroService.UserManager.
  - `common/` gets files from SysWeaver.HttpServer and MicroService.FileUploader (`fileUploader.js`).
  - `ai/` and `icons/` are assets only.

  Files from different projects reference each other by plain relative names. Nothing checks at build time that the other project is present: a missing optional project shows up as a 404 for its script, and the pages feature-test for its globals (`typeof PassKey !== "undefined"`).
- **Templates.** A few files are served with `${Variable}` substitution (see [`help/Templates.txt`](../SysWeaver.HttpServer/srcWeb/help/Templates.txt)): `index.html`/`debug.html` (title), `app/manifest.json`, `app/Home.html` and `common/theme.css` (colours of the `application` theme). The explorer listing page uses its own `$(VAR)` placeholders and is generated by `ExploreHttpServerModule`. No other web file is a template.
- **Translation.** Strings wrapped in `_T(...)` / `_TF(...)` are rewritten on the server by the translation transformer (FileTranslation `JsTranslation`), so their arguments must be literals.
- **The API lives next to the pages.** C# services publish their API with `[WebApiUrl]`. Many put it under the same URL folder as their pages, e.g. `../chat`, `../edit`, `../ServerManager`, `../upload` and `../mediaView/Api/`. This is why those pages can call the API with bare relative names such as `sendRequest("Join")`. Other pages use `../Api/<service>/<Method>`.
- **Server-side registration.** Pages are attached to the app through C# attributes and service registrations, not through any client-side routing:
  - Menu items: `[WebMenuEmbedded]`, `[WebMenuLink]`, `[WebMenuLinkExternal]`, `[WebMenuJs]`, `[WebMenuPath]`, `[WebMenuTable]`, `[WebMenuChart]`.
  - Table row links: `[TableDataUrl]`, where a prefix `*`, `+`, `^` or `-` selects the target `_self`, `_blank`, `_top` or `_parent`.
  - File-type viewers and editors: `ServiceManager.TryAddExtensionViewer` / `TryAddExtensionEditor`, e.g. `mediaView/MediaView.html?link={0}` and `edit/text.html?r={0}&u={1}&d={2}`.

## Code conventions

- **Classic scripts only.** No ES modules, no bundler, no namespaces and no build step for JS beyond compression. `common.js` alone defines about 200 globals. Other files add global functions and classes; the exception is PassKey, which uses ES classes with static members and `#private` fields.
- **Load order is the contract.** HTML pages load `../common/common.js` first with `defer`, then (optionally) `../app/application.js`, then component scripts, then the page script.
- **Dynamic loading** uses `includeJs` / `includeCss` (deduplicated through `window.IncMap`), often resolved relative to `document.currentScript.src`. That is why several scripts must be loaded as plain `<script>` tags, and why some static fields are initialised at evaluation time. Examples: `Edit.Init()` loads about 14 editor scripts, `MediaPlayer.Create()` loads the player class for a type, and chat loads `md5.js`, `UZIP.js` and `fileUploader.js` on demand.
- **Pages build their DOM in JavaScript.** HTML files have an empty `<body onload="xxxMain()">`. The UI uses unregistered custom element names (`SysWeaver-*`, `icon-WxH`) styled by tag selectors.
- **State lives in closures and on DOM elements.** Many components keep their state in a large closure (`Chat.addChat` is about 2500 lines, `CanvasChart.addChart` about 2000) and in expando properties on DOM nodes (`OnChange`, `SetStatus`, …). Few components have an explicit object model or a teardown path.
- **Naming** mixes PascalCase (`Fail`, `Open`, `AddLoading`, `PageLoaded`) and camelCase (`sendRequest`, `includeJs`, `getUrlParams`).
- **Duck-typed interfaces** are used instead of class hierarchies: media players, editor type handlers (`AddEditor` → `{SetValue, UpdateValue, Focus, DefValue, …}`), and effect texture providers.

## Page life cycle

1. The `common.js` script evaluates:
   - static fields initialise (`SessionManager.Current`, `ValueFormat.Current` and the `InterOp` bus);
   - the file ends with `SessionManager.Create(); SysWeaverInit();`.
2. `SysWeaverInit()` runs, not awaited:
   - it reads the URL flags `settheme`, `usetheme`, `css`, `mobile`, `colorscheme`, `ignoreuserchanges`, `transparent` and `fillscreen` (`noloader` is read by `AddLoading`);
   - it applies the theme and sets up fade-in for `img` / `iframe` (`data-sw-fade*`);
   - it sets `window.Mobile`, the `Sw*` layout classes and the `SwLayout` / `SwOrientation` events;
   - it registers the InterOp handlers and starts `SessionManager.Init()` (leader election and long-poll).
3. The page's `onload` main function runs. It typically calls `AddLoading()`, fetches data, builds the DOM and then removes the loader.
4. The loader remover calls `PageLoaded()`, which:
   - posts `PageLoaded` to the parent and `LoaderRemoved` to the top window (the shell uses this to reveal the iframe);
   - posts InterOp `WindowLoaded`;
   - restores the scroll position.
5. In-place navigation inside a frame goes through `Open(url, "_self")`, which posts `IframeNavigating {Url}` to the top window so the shell can record history.

## The application shell

- `index.html` loads `common/common.js`, `app/application.js` and `app/app.js`, plus `common/theme.css`, `app/application.css` and `app/app.css`. The server returns `app.js` and `app.css` empty unless an application module supplies them. These two files are the hook for application customisation, together with the optional global `window.AppMain()`.
- `appMain()` → `App.Create()` builds three regions: `app-header` (menu, back, pin, title, user and settings buttons), `app-menu` and `app-content`. It then makes these calls one after another:
  1. `Api/application/GetMenu("User")`
  2. `Api/auth/GetUser`
  3. `GetMenu("Theme")`
  4. `GetMenu("Default")`
- **Menu model.** `GetMenu` returns `WebMenu{RootUri, Items}` with `WebMenuItem{Id, Name, Type, Title, IconClass, Data, Children, Flags}`.
  - The tree comes from `/`-separated Ids in the C# attributes and is sorted by Order, then Name.
  - It is filtered per session: Auth `null` means public and `""` means any signed-in user. `NoUser` items show only when nobody is signed in, and an optional `Dynamic` callback can remove an item.
  - Item types:

    | Type | Behaviour |
    |---|---|
    | 0 | Folder |
    | 1 Table | Embeds `explore/table.html?q=../<Data>` |
    | 2 Embedded | Embeds the URL in `Data` |
    | 3 Link | Navigates the whole window |
    | 4 LinkExternal | `window.open` (new tab) |
    | 5 Js | Calls a global function or `eval`s the string |
    | 6 Chart | Embeds `chart/chart.html?q=../<Data>` |

  - Welcome (NoUser) and Home (any user) both have order -100, so exactly one of them is the first item, and that item is the start page.
- **Hosting.** All content runs in a single iframe inside `app-content`.
  - `MainMenu.EmbeddContent` swaps the iframe with a fade and pushes `history.pushState(url, "", "#" + Base64(url))`. On start, the Base64 hash is decoded and opened.
  - The new frame is revealed on `LoaderRemoved`, or 1 s after its load event.
  - When it is revealed, the shell adds `html.Embedded` to the frame, highlights the menu row (by exact URL match) and sets the titles.
- **What content pages must do:**
  - be served one folder below the root, so that `../common/` resolves;
  - have a transparent body and support `html.Embedded`;
  - use `AddLoading` / `PageLoaded`;
  - navigate with `Open`;
  - load `app/application.js` only if they use the pop-ups.

## Server communication

- **Helpers.**
  - `sendRequest(url, obj)` sends a JSON POST. The body is built by `ToTypedJson`, which puts `$type` first.
  - `getRequest(url)` sends a GET. A single argument can be passed as JSON after `?`, e.g. `GetServiceCpuChart?"svc"`.
  - `sendRequest` also supports GET encodings (raw JSON, `_d<base64url deflate-raw>`, `_u<base64url>`), but a `//DEBUG_BEGIN` block forces POST.
- **Auth.** The client never sends auth headers or tokens. Everything relies on the session cookie `SysWeaver.Session.<AppName>`.
- **Errors and redirects.** A non-200 response throws `Error("status - text")`; `sendRequest` can retry through an error handler. A redirected response navigates the page (`Open(res.url, "_self")`) and returns `null`.
- **URL bases vary:**
  - Some calls resolve against the location of `common.js` (`Api/application/GetMessages`, `serverTime`).
  - Some are root-absolute (`/Api/GetExtensionEditor`, `/Api/GetExtensionViewer`).
  - Some are page-relative (`../Api/...`, bare names).
  - The shell uses root-relative URLs, so it only works from a root page.
- **Polling patterns.**
  - Session push messages use one long-poll per browser, covered in the next section.
  - Tables poll using the `Cc` change counter and `RefreshRate`; charts poll their `q` URL (15 s by default).
  - ServerManager runs 5 s polling loops built on `delayWithAbort`.
  - fakeEmail has its own long-poll, `GetEmails{Version}`.
  - Nothing uses WebSockets or EventSource.

## Push messages and the session manager

- **One master window per browser origin.** The master is elected with `navigator.locks` ("SysWeaver.SessionManager") plus a 100 ms Ping/Pong. Other windows retry every second. When the master unloads it hands over its state with `MasterClosed{Cc, ServerEvents}`.
- **The master long-polls** `Api/application/GetMessages {Cc, MessageTypes}`. It rebroadcasts each server message over InterOp (`From:"Server"`) and syncs the server clock into `SysWeaverServerTimeOffset`.
- **Subscriptions** are reference-counted through `SessionManager.AddServerEvent(name)` / `AddMessageHandler`. Examples:
  - chat subscribes to `chat.{post|replace|remove|clear}.<provider>.<chatId>`, lower-cased;
  - AI responses stream as repeated `chat.replace` messages with `Flags & 1` (IsWorking) set until done.
- **Forced message types** reach every session: `user.login`, `user.logout`, `server.*`, `reload`, `refresh`, `filereload`. Top windows react as follows:

  | Message | Reaction |
  |---|---|
  | `server.connect` / `server.reconnect` | Reload if the server instance id (kept in `sessionStorage`) changed |
  | `server.pause`, `server.restart`, `server.shutdown`, `server.error` | Show a full-screen block |
  | `reload`, `refresh`, `user.login`, `user.logout` | Reload the page, unless the page opted out with `SysWeaverIgnoreUserChanges()` (auth pages do) |
  | `filereload` | Flush caches and re-set matching `src` / `href` attributes |

## Window, frame and tab messaging

There are three independent layers:

1. **InterOp**: the BroadcastChannel `"SysWeaver"`, with messages `{Type, From, MagicXyz:"SysWeaver"}`. When BroadcastChannel is unavailable it falls back to `postMessage` and patches `window.open`. Known message types:
   - `Theme.Changed`: chart re-reads its colours.
   - `UserImageChanged`: the shell refreshes the avatar.
   - `WindowLoaded`.
   - `FileSaved` / `FileDeleted`, sent by the text editor; no listener exists.
   - The media editor protocol `<prefix>GetProps/SetProps/Reload/SetVolume/UpdateSize/Crop/Compile`.
   - The session manager's master election and fan-out of server messages.
2. **Raw `postMessage` between frames and their parent or top window**, as untagged `{Type}`, sent to target `"*"`. Receivers do not check the origin.
   - Frame → shell: `PageLoaded`, `LoaderRemoved`, `IframeNavigating{Url}`.
   - Chat: the parent sends `chat.scrolltop|scrollbottom|showall|hideall|clear`, and the chat sends `ViewProfile` back.
   - Chart: `ChartClick` out (no listener).
   - Media players: `MediaPlay/Pause/Stop/Once/Loop/Mute/UnMute/SetVolume/Seek/CustomX..Z`.
   - `ParseTools.MessageProxy` relays messages for iframe wrappers.
3. **Direct same-origin DOM access.** The media dark-mode detector observes `window.top`'s `<html>`, `GetElementFromId` walks up the parent frames, and the shell adds `html.Embedded` to the frame's document.

## Theming and layout

- **Theme resolution order:**
  1. `?usetheme` (`window.UseTheme`)
  2. `localStorage["SysWeaver.Theme"]`, set by `?settheme` or by `setTheme()` from the server's Theme menu (`[WebMenuJs]`)
  3. The OS `prefers-color-scheme`
  4. `"dark"`
- **Applying a theme.** `light` removes `data-theme` from `<html>`. Any other theme sets `data-theme=<name>`; `theme.css` defines `dark`, `hacker`, `application` and `pro`. `application` takes its colours from the server template variables `${Color.Background|Color|Acc1|Acc2}`.
- **Derived variables.** JS derives `--Theme{Background,Main,Acc1,Acc2}{R,G,B,RGB,25,50,75}` and sets `IsDarkMode`. `--ThemeIconSize` scales icons. Icons are CSS mask images from `icons/*.svg`. Many icon classes are defined in consumer CSS rather than centrally.
- **Theme in embedded pages.** The shell forwards a forced theme to embedded pages with `?useTheme=`, and theme changes are broadcast as `Theme.Changed`.
- **Layout.** Layout state is expressed as body classes: `SwPinned`, `SwCollapsed`, `SwNarrow` and `SwMobile` (shell), and `Sw*` set by `common.js`. These are re-applied on the `SwLayout` event. `window.Mobile` and `localStorage["SysWeaver.Mobile"]` override detection.
- **fakeEmail** has its own, separate theme system.

## Authentication on the client

- **Shared base.** All `auth/` pages are empty shells that load common, `Auth.js`, `AuthUi.js` and then the page script. MicroService.Auth provides that base:
  - `Auth.js`: requests, password policy, leak check against pwnedpasswords, e-mail and phone validation;
  - `AuthUi.js`: the widgets, `AuthPage`, `AuthStartPage` and `AuthPageValidation`;
  - `Auth.css`.

  PassKey is an optional plug-in. UserManager supplies `validateShortCode`/`cleanUpShortCode`, which `AuthUi.js` calls without a guard.
- **Password login:**
  1. `GetUserSalt(user)` returns `[salt, oneTimePad]`.
  2. The client computes `h = SHA256b64(pw|salt)`; if the salt starts with `|`, it hashes the binary salt followed by the password instead.
  3. It POSTs `Api/auth/Login {OneTimePad, Hash: SHA256b64(h|pad)}`.

  If `GetUserSalt` fails, the client falls back to Basic auth through `../basic_auth` and `../login`. Logout is `GET ../logout` with `Authorization: Basic logout`.
- **Passkeys.** The client fetches a challenge in advance, calls `navigator.credentials.get` or `create`, then submits the result (`Auth`, `Create` or `New`). The login page also uses conditional-mediation autofill.
- **After a sign-in**, `AuthStartPage` waits 3 s, replaces the URL with the app root and reloads. The other open windows reload through the `user.login` push message.
- **Short codes.** E-mail and SMS steps store a short code in the server session. The page then continues at `<Page>.html?<code>`, and the code is valid only in that same session.
- **Token parameters differ between pages.** Some pages treat the whole query string as the token, some read `?token=`, and some server-built links use `?user=&salt=&token=`.

## Integration with native hosts

- **Thumbnail rendering.** SysWeaver.MicroService.Thumbnail.Web loads `mediaView/MediaPreview.html` or `MapView.html` in CefSharp or WebView2 and injects a `ScreenShotHost` object (`isSupported`, `setSize`, `doIt(duration, fps, error, loadTime)`). The URL formats of these two pages are therefore an external contract.
- **Shader errors** are reported to the host through `ErrorText.SetText`.
- **External services:** Google Maps Embed (OpenStreetMap when there is no key), `fonts.gstatic.com`, pwnedpasswords and YouTube embeds.

## Contracts mirrored between C# and JS

None of these JS definitions are generated; they are hand-written copies of C# types or conventions:

- **Table and type info:** `TableDataProps`, `TableDataFilterOps`, `TableDataFilter` and `TableDataState` (from `SysWeaver.Common/Data`); `HttpServerEndpointTypes`; `TypeMemberFlags`.
- **Media:** `MediaTypes` and the `MediaPlayerParams*` defaults.
- **Status and format values:** upload status codes −12..2, chat message Format and Flags values, StoreFile and StoreLink scopes, menu item Types and Flags.
- **Shapes of server responses:** `ApiInfo`, `ExploreData`, `ChatJoinResponse`, `ChartJsConfig`.
- **String-encoded metadata:**
  - enum metadata packed into `Default` as `def>v<name<summary<remarks|…`;
  - `Hide:<js expr>`;
  - the effect parameter comments `// var:{…}`;
  - the `[TableDataUrl]` target prefixes.
- **Names derived by string replacement:** the `*HistoryChart` / `*HistoryShortChart` URLs, and the repository names `Keys`, `Current_<svc>` and `Master_<svc>`.

The folder READMEs note the places where a JS copy currently differs from its C# source.

## Structural observations for the refactoring

- **Global namespace and load order** are the main implicit contract. A move to modules would have to replace three things: `document.currentScript.src`-relative loading, static field initialisation at evaluation time, and globals called across projects (`AddTypeName`, `validateShortCode`, `PopUp` from `ValueFormat`, the `EditType<Spec>Factory` plug-ins).
- **`application.js` has two jobs.** It is both the shell and the shared pop-up library, so every page that wants a pop-up loads the shell code too.
- **Large closures with state stored on DOM elements** in chat, chart, table and editor make the components hard to reuse and leave them without a teardown path.
- **Duplication worth consolidating:**
  - the password hashing protocol, copied 9 times across the auth projects;
  - the near-duplicate blocks in `UserManagerUi.js`;
  - the three `*EffectsLib.html` pages and the four effect index pages;
  - the Image/Text and Video/Audio players;
  - `BeginElementChildUpdate`;
  - the `UploadCompleted` handlers;
  - Desktop vs Mobile editor CSS;
  - `icons.css` vs `logo.css`;
  - the HTML `<head>` boilerplate in every page;
  - `delay` / `waitEvent2` copies outside `common.js`;
  - the speech classes inside `chat.js` (`SpeechGen`, `SpeechInput`), which are general purpose.
- **Unused or orphaned items** (no in-repo caller or listener):
  - `common/common.css`, `app/tags.js`, `EditTypeLanguage.js`;
  - the `ChartClick` and `FileSaved` messages;
  - several common helpers (`Cache`, `ProgressBar`, `PostTop`/`PostParent`/`PostAll`, `GetServerTime`);
  - auth wrappers such as `setNickName` and `isManagedUser`;
  - Hammer.js, which the chart page loads but never uses.
- **Product-specific coupling inside the framework:** media uses `QuizzWeaver.*` storage keys, the `QuizzRights` global and the `../quizz/` API.
- **Outliers in style:** fakeEmail uses none of the shared code (its own fetch, toasts and theme), and PassKey uses ES classes with private fields.
- **Strings are not translated consistently.** Many are hard-coded English rather than wrapped in `_T`/`_TF`; this matters for any refactor that touches strings, because the translation rewrite relies on literal arguments.
