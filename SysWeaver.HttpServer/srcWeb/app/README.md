## Purpose

The application shell (header, main menu, content frame) is built by `index.html` with `sw/shell.js` (sources and documentation in [`../shell`](../shell/README.md)); `application.js` / `application.css` here are its legacy compatibility bundles for old format pages. Applications customise it with `app/app.js` and `app/app.css`; when no module provides these, the server serves empty files. `app/app.css` is the brand stylesheet of the whole app: the shell links it and `Sw.Theme` applies it to every other page too; themes registered in `app/app.js` reach every page (see [`_docs/WebBranding.md`](../../../_docs/WebBranding.md)). The Home and Welcome pages are registered as menu entries on [`HttpServerBase`](../../HttpServerBase.cs) (`app/Home.html` for logged in users, `app/Welcome.html` for everyone).

## Behavior (web analysis)

### Loading and initialization

- **Shell boot:** the root page `index.html` loads `sw/core.js`, `sw/ui.js`, `sw/shell.js` and `app/app.js` (defer) and starts the shell with `<body onload="appMain()">`; the shell is described in [`../shell/README.md`](../shell/README.md). `app/app.js` and `app/app.css` are always requested and served empty unless an application supplies them; an `app.js` usually defines `async function AppMain()`, awaited before the first page opens.
- **Legacy bundles:** [`application.js`](application.js) and [`application.css`](application.css) are GENERATED by `SwWeb bundle` (see [`../sw/bundles.json`](../sw/bundles.json)): the shell sources plus [`../shell/compat_application.js`](../shell/compat_application.js) / [`../shell/compat_application.css`](../shell/compat_application.css), which define every global of the old application.js (`PopUp`, `Confirm`, `PopUpMenu`, `PopUpSelection`, `SearchablePoupSelection`, `PopUpEdit`, `PopUpWorking`, `WebMenu`, `WebMenuItem`, `MainMenu`, `MainMenuStyle`, `App`, `AppParams`, `appMain` ...). Old format pages load them after `../common/common.js`; never edit them.
- **Dynamic includes:** `home.js` loads `../common/fileUploader.js` with `Sw.Net.IncludeJs` only when `CustomUserImageService` exists (fileUploader.js loads `md5.js` itself). Pages in other projects (`explore/table.js`, `chart/chart.js`) load `../app/application.js` themselves to get the legacy pop-up functions.

### Files

All three pages are new format pages (`../sw/core.js`, `../sw/ui.js`, `../common/theme.css`, `../sw/ui.css`, `class="sw-root"` on the body), started by `<body onload="...Main()">`, and use the page protocol: `Sw.Page.Loading()` while starting; its remover posts `LoaderRemoved` so the shell reveals the content frame.

#### `Home.html` / `home.js` / `home.css`
- `Home.html` is a server template; its template variables are `${#EnvInfo.AppDisplayName}` (`h1.AppName`, `translate="no"`, the same variable as the `index.html` title), `${#EnvInfo.AppDescription}` (`translate="no"`) and `${#Session.NickName}` in `span.HomeGreeting` (with a `data-translation_context` that names it as `${@Session.NickName}`). Order: `header.HomeHead` (`<img class="UserImage" src="../auth/UserImages/Current/small">`, the name, the welcome text and the description), `section.HomeKpis`, `section.HomeCards` and `p.HomeHint`, in `<main class="Home">`; Home shows no logo. Home.html and Welcome.html link `app.css` (the brand stylesheet) last and render blocking, so no frame shows the default brand.
- `homeMain()` titles the user image "Your user picture" (it is the user's avatar; shown exactly as the server serves it: the uploaded picture or the server generated one) and, inside the shell: `homeQuickLinks` adds `section.QuickLinks` before the hint (from the shell window's `SysWeaverApp.GetQuickLinks()`: "Most used" = the pages this browser opened most often and at least twice (`MinCount: 2`), `localStorage["SysWeaver.RecentPages"]` kept by the shell, "Recently visited" = the last visited pages not in "Most used" (no page is listed twice), and "Shortcuts" = the top level menu pages: cards while there is no history, else, as they repeat the menu, a collapsed `details.QuickGroup.Collapsed` ("Shortcuts" summary `summary.QuickSummary`, closed) holding a compact row of chips `ul.QuickList.Compact` (icon + name, description in the tool tip); `button.QuickLink` with the menu icon, name and a description of up to two lines (full text in the tool tip) opens the page like its menu item; `main.HasLinks` makes the head compact: a smaller name, little spacing, content from the top), `homeHint` fills `p.HomeHint` (phones: where the menu is; keyboard devices (`Sw.Shell.HasKeyboard`): plus the Alt+M hot key; touch devices: no key hints), `homeStatus` appends `p.HomeStatus` (green / red dot, "Connected to the server, server time hh:mm" or "Not connected to the server", refreshed every 10 s). `homeKpis` adds `section.HomeKpis` after the user card: the server uptime from the template attribute `main.Home[data-appstart]` (`EnvInfo.AppStart`, UTC) and the synced server time ("4 h 59 min", "2 d 3 h"), the application version (`homeVersion`: `main.Home[data-appversion]` = `EnvInfo.AppVersion` (`AppInfoParams.AppVersion` of the `*.Services.json`, else the executable version), shown without a `+<revision>` suffix, the full version and the build time `data-appbuild` = `EnvInfo.AppBuildTime` in the tool tip), and for users with the admin or ops token on a server with `SysWeaver.MicroService.ServerManagerService` (`Api/auth/GetUser`, `Api/HaveService`, `ServerManager/GetServerInfo`, the Server page call) tiles for CPUs, memory (2 decimals like the Server page, "63.35 GB"), processes and drives that open the Server page / process / drive tables; no new server api, failures only leave tiles out. The template text is unchanged.
- Dashboard data: the *Problems, last 24 h* tile, the header status and the *Problems* card come from the exception trackers (`Api/debug/ProblemsTable`: every tracked failure is counted there, not every one is logged): the number of parts that failed in the last 24 h, the latest 3 with *Failing* / *Failed* badges, *Open Problems*; servers without the problems table fall back to the warnings and errors of `Api/debug/LogTable`. The server rows (*Managed services* tile, facts strip) show for every user who may call `ServerManager/GetServerInfo` (`Sw.Access.CanCall`, no token names in the page).
- `homeMain()`: shows the loader, asks `Api/HaveService("SysWeaver.MicroService.CustomUserImageService")`; if the service exists it loads `common/fileUploader.js` (`Sw.Net.IncludeJs(null, "fileUploader.js")`, which loads `md5.js` on demand; `UZIP.js` is no longer needed) and makes the user image an upload target with `Sw.Upload.Target(img, {Repo: "UserImage", Accept: "image/*", Title, OnStart, OnResults})`: click, Enter / Space (keyboard focusable, role button) or drop an image. `OnStart` shows an info toast; `homeUploaded` reports the first file: `AlreadyUploaded` -> info + InterOp `UserImageChanged`; `None` -> info, the image switches from `.../small` to `.../large` (or reloads with a cache flush) + `UserImageChanged`; other codes -> a fail toast with `Sw.Upload.StatusText`.
- `home.css`: the header (`.HomeHead`: user picture, `h1.AppName`), muted description, `.UserCard` (tinted chip), `.HomeHint` (hidden when empty), `.QuickLinks` / `.QuickGroup` / `.QuickHeading` / `.QuickList` (auto fill grid, `.Compact`: a wrapping row of chips; `details.QuickGroup.Collapsed` with `.QuickSummary`, a toggle heading with an arrow) / `button.QuickLink` (`.QuickIcon`, `.QuickName`, `.QuickDesc` (two lines)), `.HomeStatus` (`.StatusDot`, `.Offline`), `.HomeKpis` / `.KpiList` / `.Kpi` (`button.KpiLink`, `.KpiIcon`, `.KpiValue`, `.KpiLabel`; phones: an even two column grid with icons, an odd first tile (uptime) spans the row), wider link grid on large screens, `.Home.HasLinks` (compact head at the top: smaller name and user picture, less spacing; windows <= 500 px high: no logo / description, links above the fold), `.UserCard h2` (normal text color), `img.UserImage` (at least a touch target, shown at once), `.CanUpload` with hover / focus ring and the upload states `Dragging`, `Selecting`, `Uploading` (set by `Sw.Upload.Target`).

#### `Welcome.html` / `welcome.js` / `welcome.css`
- A static page (not a template) with the logo and an empty `h1.AppName` (`<main class="Welcome">`, `img.Logo`). `welcomeAppName()` reads the application name from the shell window (`top.SysWeaverAppTitle`, the templated index.html title); stand alone (or before the shell set it) `Sw.Page.AppName()` reads `name` of the templated `app/manifest.json`, and the tab title becomes "<app name> - Welcome"; only without any name the heading is removed.
- `welcomeMain()` fills the name and probes `Api/auth/GetUserSalt("dummy")` (a 404, no auth service, means "no sign in" and is not reported). When signing in is available the logo gets class `Click`, a `p.Lead` ("Sign in to continue.") and a large primary `Sw.Button` (class `SignIn`, icon `login`, text "Sign in", tool tip "Click to sign in") are added and the button is focused (after the loader released the focus; `focusVisible: false`, so no focus ring shows until the keyboard is used). Both call `welcomeSignIn`, which navigates with `Sw.Page.Navigate("../auth/Login.html", "_self")`: inside the shell the `IframeNavigating` message updates the history and the deep link hash before the frame navigates.
- `welcome.css`: centered column (42% from the top), logo (`--size` = min(60vw, 30vh), a third of its height clear below it; `img.Logo.Click` gets a soft frame on hover / focus, never an effect on the mark itself), `h1.AppName`, `p.Lead`, the large `button.SignIn` (1.25x touch height, larger font).

#### `manifest.json`
- A template (`$` JS-string transforms): `start_url` and `scope` = `../` (relative to the manifest, so the site root as the browser sees it: an installed app works below a reverse proxy sub-path and the internal host is never in the file), `short_name`/`name`/`description` from `EnvInfo`, `theme_color` = `${$Color.Color}` and `background_color` = `${$Color.Background}` (the application colours, `HashColors.AppColors`), icons `../icon.svg` (any), `../icon-180.png`, `../icon-192.png` and `../icon-512.png` (all generated per app by the server, `HttpServerBase_Favicon.cs`; no maskable icon), `display: fullscreen`, `screenshots` = `../logo.svg` (1024x768), `sysweaver_optimized_send` = `${Client.OptimizedSend}`.

#### `tags.js` / `tags.css`
- Optional library (no first-party consumer). New API `new Sw.TagsGallery({FindTags, GetTags, RemoveTag, AddTag, MaxTagCount, Options})` (`.E`, `Update()`, `GetTags()`, `Ready`); the legacy globals `TagGalleryParams`, `Tag`, `FilterTags`, `SetTagClassName`, `CreateTagsGallery` keep their signatures and results (`{Element, Update, GetTags}`).
- Renders `<SysWeaver-TagsGallery>` (role list, `Embedded` / `options.Class`) with one `<SysWeaver-TagEdit>` (role listitem, `tag.Class`, title `Desc`) holding `<SysWeaver-TagText>` and, with `RemoveTag`, a ghost `Sw.Button` (icon `RemoveIcon`, busy while removing). With `AddTag` and fewer than `MaxTagCount` tags an Add `Sw.Button` (class `TagAdd`, first or last) opens `Sw.Dialog.Select` over `FindTags(search)` (all tags with `ShowAllTags`, else only after typing; existing codes excluded; keyboard: type, arrows, Enter). Failures show fail toasts (`AddError` / `RemoveError` / `SearchError` / `FilterError` + the message); the gallery re-renders after each change.
- `tags.css`: Sw token based chips (touch sized, `--sw-accent1`), `.Keep` (green) / `.Ignore` (blue) variants, `.Embedded`, icon classes `IconTagAdd` / `IconTagRemove`.

**How the menu is built on the server (`WebMenuService`):**
- Menu items come from attributes in `SysWeaver.MicroServices/WebMenu`:
  - on service classes: `WebMenuEmbedded`, `WebMenuLink`, `WebMenuLinkExternal`, `WebMenuJs`, `WebMenuPath`, `WebMenuTable`;
  - on API methods: `WebMenuTable` / `WebMenuChart`, where `Data` defaults to the API URI.
- Each attribute names a menu (`null` = `"Default"`) and a `/`-separated `Id` path that defines the tree. Missing parents are created automatically as Path items.
- `GetMenu(menu)`:
  - concatenates the requested comma-separated menus and sorts by key, so parents come before children;
  - drops an item if its `Auth` does not match the session (`""` = any logged in user, `null` = no requirement), if it is a `NoUser` item while a user is logged in, if its parent was dropped, or if its optional `Dynamic` callback returns false;
  - sorts siblings by `Order`, then by `Name`, and removes empty Path folders.
- `HttpServerBase` itself registers:
  - `Welcome` (`app/Welcome.html`, NoUser, order -100) and `Home` (`app/Home.html`, auth `""`, order -100), so exactly one of them is the first item;
  - the `Theme` menu (Js items `if(setTheme('…'));false`, which return false so the menu stays open);
  - the `Debug/Http Server` and `Debug/Data` folders.
- The auth services fill the `User` menu with Embedded `auth/*.html` pages (Login, Logout, SignUp, passkeys, password, email and phone management, …).
- Templates used here: `app/Home.html` and `app/manifest.json` (registered with `AddTemplateMatch` in `HttpServerBase`).

### Dependencies

- **Legacy bundles need:** `common/common.js` (sw/core.js + sw/ui.js + the old common.js globals) loaded first; `common/theme.css` supplies the theme variables and `html.Embedded`.
- **Needs from elsewhere:** `Edit`, `EditOptions` and `TypeMemberFlags` from `edit/` (SysWeaver.MicroService.Edit, only for `PopUpEdit`); `Sw.Upload` (common/fileUploader.js, SysWeaver.MicroService.FileUploader, only for Home); icons from IconModule; `explore/table.html` and `chart/chart.html` for Table and Chart menu items.
- **Consumers:**
  - `index.html` (the shell, through `sw/shell.js`);
  - many pages that load `../app/application.js` and `../app/application.css` for `PopUp`, `Confirm`, `PopUpMenu`, `PopUpSelection` and `SearchablePoupSelection`: explore table/api, chart, edit, chat, media view, server manager, log file, passkeys, KeyMan, user storage;
  - `app/app.js` provided by applications (`AppMain` hook).

### Structural observations

- **Generated legacy bundles.** `application.js` / `application.css` are build outputs of `SwWeb bundle` (sources: [`../shell`](../shell/README.md)); edit the sources and rebuild. The old monolithic application.js (shell + pop-up library in one classic script) was replaced by the Sw ui library (dialogs, menus), the Sw shell and a thin compatibility layer.
- **Implicit contract for embedded pages** (unchanged). Hosted pages run in an iframe inside `<app-content>` and are expected to: use `Sw.Page.Loading` / `Sw.Page.Main(fn, {Loading})` (or the old `AddLoading`), which posts `LoaderRemoved` when done so the frame is shown early (otherwise 1 s after load); navigate with `Sw.Page.Navigate(url, "_self")` (or the old `Open`), which posts `IframeNavigating` so the shell records history; support the `html.Embedded` class and a transparent background.
- **Tags gallery:** `tags.js`/`tags.css` are not referenced by any first-party page (an optional library, rewritten on Sw with the legacy API kept).
